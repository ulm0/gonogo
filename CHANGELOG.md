# Changelog

All notable changes to gonogo. Versions follow [Semantic Versioning](https://semver.org/); before 1.0.0 a minor release may break things.

## Unreleased

## 0.21.0 (2026-11-24)

The boss can hire on demand within rules you set, stop agents with fire_agent and keep a hired crew under a daily dollar ceiling; budgets per engine or provider; Search by meaning can run its own Ollama; and opencode no longer falls back to a free model on its own. Before you update: the Docker image grows by about 30 MB (compressed) because it carries Ollama's CPU part (79 MB unpacked); an opencode agent on an anthropic/... model (or any non-opencode/ model) without that provider's key now stops at "needs you" instead of quietly running a free model; hire by rule and fire_agent exist, but automatic approval is off by default, so every hire still waits for your GO until you turn it on, and FLIGHT can stop any agent but itself unless you protect it. Not verified: the Hire on demand block, the protect box and the Ollama block in a browser; the crew and engine budgets holding live pi or opencode agents; managed Ollama on arm64, macOS and Windows and on a real Clean Room network (see What was not verified).

- **Hire on demand, within rules you set.** The boss can hire inside rules you write: a rules file `relief.json` and `PUT /api/relief/rules` (with the password again), automatic approval of a `hire_agent` that fits every rule (position, engine, mode up to `auto`, folder, crew size, hires per hour) with the agent marked *hired by flight*, the rule named when a request still waits for your GO, `auto` mode in a request, a STOP CREW call, and Downlink and Black Box lines. **Automatic approval is off by default**: until you turn it on, every hire still waits for your GO.
- **The boss can stop agents with `fire_agent`.** The agent ends and can be started again, and its open tasks go back to the Flight Plan unassigned. Only FLIGHT itself is fixed: the boss can stop any other agent, yours included, unless you protect it in its Edit form (a switch in Flight Rules, *FLIGHT may stop agents*, turns this off). It is refused for a protected agent and for one that waits for you. Flight Rules has a new *Hire on demand* block with the rules, SAVE RULES and STOP CREW.
- **A dollar ceiling on hires by rule.** With a daily crew budget set, Propellant holds the agents the boss hired by rule once together they have spent it, and no further hire by rule is made until the next day or a higher ceiling. A rule can also list the models each engine may use, and `hire_agent` takes a `model`.
- **opencode never falls back to a free model on its own.** An opencode agent runs opencode's free models only when you pick one (`opencode/...`). With another model whose provider has no key for the agent, it now asks you (needs you, with what to do) instead of quietly running on a free third-party model. Flight Rules says when a saved opencode default lacks `provider/`.
- **Budgets per engine or provider.** A dollar budget can now be set for an engine (claude, pi, opencode) or a provider (anthropic, opencode, openai), over the use of that engine or provider. At 100 % only its agents are stopped; the rest of the room keeps working. Set with the API for now.
- **Search by meaning: gonogo can run its own Ollama.** The block has two modes. **Managed** (the default for a new setup, Linux x64 and arm64) needs nothing installed: the Docker image carries the pinned Ollama (the CPU part of 0.40.18, 79 MB), and anywhere else gonogo downloads that release once (1.6 GB, checked against a pinned sha256 before it is opened, 79 MB kept), starts `ollama serve` itself when an entry has to be indexed (on `127.0.0.1` and a port of its own, in its own process group, with an environment of its own), pulls the model with progress, restarts it with a backoff if it dies, stops it when it is idle, over a memory limit, when the feature is turned off and when gonogo stops, and shows its state, memory, settings and log. **Remote** keeps every rule of the endpoint and the confirmation, and takes an API key for an Ollama behind a proxy (sent as `Authorization: Bearer`, over https or to this machine only; kept in its own 0600 file and never shown). Embedding on a CPU takes about half a second a piece: an index of 2,000 pieces takes about 20 minutes in the background. Where the Clean Rooms share gonogo's network (the Docker default), an agent in one can reach that Ollama, which has no login: managed is then not the default and is saved only after the Director says he understands (a box in the block, `acknowledge: true` in the API). Only the pinned version is run: a copy that does not say so is not used.
- **Code scanning alerts addressed.** The docs workflow no longer keeps a dependency cache when it builds a branch picked by hand, so a branch cannot leave a cache for the default branch to restore; the rest are tidy-ups in tests and one call in the server, with no change in behavior.
- **Dependabot security updates.** `.github/dependabot.yml` lists the project's ecosystems (npm at the root and in `scripts/multivac-tool`, GitHub Actions, Docker, Docker Compose) so Dependabot security updates cover them. Version updates stay with Renovate; Dependabot's are off (`open-pull-requests-limit: 0`) to avoid duplicate pull requests.

## 0.20.0 (2026-11-24)

What needs you sits in the room under the Brief box, the model fields list the models pi and opencode really have, Cost splits use by engine, provider and model, opencode agents start with a model, and a security policy. Before you update: opencode agents now take their model from their config (opencode 2.4.1 has no --model, so on 0.19.0 an agent hired with a model exited at start); an opencode agent cannot use the owner's Anthropic sign-in and needs ANTHROPIC_API_KEY or a Clean Room with egress for anthropic/... models; run logins in the container as `docker exec -u node gonogo ...`; at start the container gives back root-owned files in a bound XDG_CONFIG_HOME only when its top is uid 1000's, or root's and empty. Not verified: an anthropic/... opencode model with a key or through egress, the Needs you list, the model lists and the key warning in a real browser, and the XDG_CONFIG_HOME repair outside a hand run in docker-in-docker (see What was not verified).

- **What waits on you is in the room, under the Brief box.** The "Needs you" list (a console asking for a go or a permission, a hire request, a handoff to send, a message that asks you something) now sits right under the Brief box in the room, and at the top of the room on a phone, newest first, each with its GO and NO-GO or its reply box. The Comms key counts what needs you (then what is unread) from any page, and "Mark handled" clears a message that needs no answer. The floods that used to dock at the foot of the room are this list now.
- **Docker: root-owned files in `XDG_CONFIG_HOME` are given back at start.** `docker exec gonogo opencode models` (or `gh`, `aws`) runs as root and left root's files in a config folder bound outside the home, which the server could not write. The start now repairs that folder like the home (files with one link and directories that are root's, never across a mount, never through a symlink), but only when the folder is a bind or volume and its top is already uid 1000's, or is root's and empty; a root-owned folder with anything in it is left alone and the log says so. Run logins and tools as the server's user: `docker exec -u node gonogo ...`.
- **Real model lists.** The model field of the hire and Edit form, and the models in DEFAULTS, now offer the models the engine itself lists (`pi --list-models`, `opencode models`) as names to pick from, with a Refresh key, and say when the engine is not installed or could not be asked. Free text still works.
- **opencode models that need a key.** An opencode agent cannot use the owner's Anthropic sign-in (its opencode data is its own), so an `anthropic/...` model needs an `ANTHROPIC_API_KEY` for the agent or a Clean Room with egress. The opencode model list says that a model of another provider than opencode's own needs that provider's key, and the hire and Edit form warn when the agent would start without it: opencode otherwise falls back to its free default model without saying so.
- **opencode agents start with a model.** An opencode agent hired or edited with a model exited at once, because opencode 2 has no `--model`; the model now goes into its config (as `provider/model`, for example `anthropic/claude-opus-5-5`), with the effort as that model's variant. A name without `provider/` is refused for opencode.
- **Cost shows use by engine, provider and model.** Each new ledger line says which engine ran the reply and which provider it called, so Opus in Claude Code and Opus in pi are separate rows. The wall's BY ENGINE AND MODEL fold and the Cost table list tokens, the estimate and the agents per row, per window, with the room total as their sum. A free model (opencode's big-pickle) shows as free, not unpriced; a price row can be per provider (`bedrock/claude-opus-5-5`); rows say whether they count against the Claude plan. Old lines show as unknown.
- **Engine Bay page says what was tested.** Each engine is marked [tested], [partly] or [not run] with its version and date, and the pi and opencode feature table marks each cell [tested], [tests only] or [not run]. pi 1.6.0 and opencode 2.4.1 ran in a real room on 0.19.0; the permission gate, Clean Room and end-of-turn mail were not seen.
- **Not-verified page brought up to date for pi, opencode, cost by engine and the Docker config repair.**
- **A security policy.** `SECURITY.md` says how to report a vulnerability privately (GitHub's Report a vulnerability), which versions get fixes (the latest release), what to expect and what is in scope.

## 0.19.0 (2026-11-24)

pi and opencode read their own input box and keep the thread across an engine switch, opencode 2.4.1 replaces opencode 1.x, and COMMS shows what waits on you. Before you update: opencode 1.x is gone, so recreate the container to get opencode 2.4.1; opencode agents keep their data in agents/<name>/opencode-data and sessions from opencode 1 are not resumed. Not verified: the Docker image was built only by CI, opencode 2 in a Clean Room was not run, and one fresh Claude Code start stayed "needs you" once after a switch (cause unknown); see What was not verified.

- **COMMS shows what waits on you, and you answer it there.** A "Needs you" strip sits above the COMMS tabs with a count: hire requests with GO and NO-GO, handoffs FLIGHT asks to send, and messages that ask you something (GO and NO-GO keys for a go/no-go, a reply box for a question). An answered one leaves the strip. A message counts as asking when it is unread and says go/no-go or has a question mark; "Not a question" clears one that only looks like it.
- **pi and opencode: the Brief box, and an engine switch that finds the old session.** pi and opencode now read their own input box like Claude Code does: text typed in a console and then erased frees the mail at once (it used to stay held for 30 minutes). An engine switch finds the old session even when an older gonogo started it (pi and Claude Code by folder and time, opencode from its own session list), the new session is told in one line which engine it came from, until when and which one it is now, and it may read handoff.md without a permission request.
- **opencode 2.4.1 replaces opencode 1.x.** The package is `@opencode/cli`. gonogo's plugin is rewritten on opencode's new plugin API (a folder with an index.js), every agent runs opencode --standalone with its own database in agents/<name>/opencode-data, the engine switch reads and finds sessions with opencode session export/list, and the Docker image installs @opencode/cli 2.4.1. opencode 1.x is no longer supported: **recreate the container to get 2.4.1** (the image installs it). An opencode agent keeps its data in `agents/<name>/opencode-data`, so **sessions started by opencode 1 are not resumed**.
- **Search by meaning no longer embeds every keystroke.** The Mission Log page shows word results while you type and asks for meaning only after 600 ms without a key, or on Enter, so typing does not spend the daily budget. With the feature off, `log_search` answers exactly as before (no note, no mode).
- **opencode: a new path under a symlinked parent is asked about.** The opencode plugin's own-folder check now resolves the nearest existing parent of a path that does not exist yet, so a new folder under a symlink that leaves the agent's folder is asked about.

## 0.17.0 (2026-11-23)

Docking 2: stations work together on a task link (hand back, recall, deliver and accept, chains, missions, cost reports, knowledge on request) with its UI; Clean Room sandbox flavors (docker, gVisor, microVM); an egress proxy that keeps the Anthropic API key out of a Clean Room container; your own Claude Code MCP servers reach the agents. Not verified: gVisor and Kata never ran for real; egress OAuth is not shipped and egress is not enforced; global MCP OAuth was not tried with a real login; Docking's stale nudge, the 7-day give-up and a lost outbox were not run, and its UI was not tried against a real server (see What was not verified).

- **Clean Room sandbox flavors.** A Clean Room console runs on docker (runc), gvisor (runsc) or microvm (Kata): a room default in DEFAULTS and an override per agent. A flavor whose runtime Docker does not list is refused, and a start never falls back to runc. The microVM cannot start until its bridge network mode exists.
- **Docking 2, the core: a link.** A task handed to another station is now bound to a link both stations hold (`dl_…`); each side owns its own fields and the other only gets events (offer, accept, status, note), numbered per author, applied once, refused when rewritten, and kept in an outbox until the other station acks them (`POST /dock/link`, `dock-outbox.json`). A task handed off stays open here; the receiver's status changes and notes travel back by themselves, without the text for a task marked `localNotes`. Offers carry `due`, `priority`, `onward` and `budget`. A station takes at most 30 tasks an hour and 20 open ones from one dock and says why when it refuses. `GET /api/links` lists the links, `GET /api/links/<id>` the trail, `GET /api/docking/outbound?dock=` (the Director's own login) what left, exactly as it left.
- **Docking 2: handing a task back and forth.** A task handed to another station can be given back (`return`), withdrawn (`recall`), delivered and accepted (by hand or `autoAccept`), with deliverable links (pr, branch, commit, file, url; at most 5, checked, never fetched). The assignee is only a hint: a name that is no agent there gives an unassigned task and a message to that station's boss, marked as not from the Director. Per-station rules (`handoff: ask|allow`, `incoming: auto|off`, `autoAccept`, `staleHours`) are set from the Director's login. The boss gets a `task_handoff` tool; with `ask` the Director reads the whole text before it leaves. Incoming tasks reach the Downlink (a digest past 3 in 10 minutes), and a quiet accepted link tells the local boss once per period.
- **Docking 2: knowledge on request, and suggestions.** The Director can mark Mission Log entries and claims shareable for named docked stations (`PUT /api/dock-shares`, his own login, with the password again); a station with `serve` on answers a docked agent's `knowledge_ask` from those marks only, with at most 5 cleaned snippets of 600 characters (secrets replaced, no id, tag, author or anchor), 20 requests an hour per dock, and the exact text that left in the Outbound view; the asker gets it as data and nothing is stored. FLIGHT's `station_suggest` ranks the agents here and docked by the words of a task and sends nothing. Text that leaves in a link event now also passes the secret redactor, and an attachment whose address holds a credential is refused.
- **Docking 2: missions and money.** A mission can be offered to a docked station like a task (the receiver makes its own planned mission, labelled with where it came from, and reports counts of its tasks, never titles; tasks handed over from the mission land inside it), a station can tell the other what a task it holds cost (`reportCost`, off by default: dollars to the cent, an estimate, one an hour and one at delivery), and the cap a peer offers for a linked task is clamped ($0.50 to the room's own budget) and enforced by the receiver's own Propellant as a `links` budget that holds only that one task.
- **Docking 2: reach, lost events and chains.** A dock message whose subject starts with `[dl_...]` is a question or reply on that link (it has to be a link with that station), events given up on after 7 days or past the outbox cap become one visible `lost` event with no hole in the numbering, an undocked station that is docked again resumes its links, a station that lost its outbox asks the other what it holds (`GET /dock/link/<id>`) and sends what is lacking, and a task can be handed on (chains and splits): only when its offer said `onward`, through 3 stations at most, never back into the chain, and with the status of the next station shown hop by hop.
- **A Clean Room agent can run without the Anthropic API key in its container.** A new switch (Flight Rules, off by default; one agent can follow or override it in its form) gives the container a placeholder and a web address of gonogo, which adds the real key to requests to api.anthropic.com. API keys only (a subscription login is not covered), and the Clean Room's network is not restricted. Changing it asks for your password.
- **Your own Claude Code MCP servers reach the agents.** The servers you added with `claude mcp add --scope user` are now read at each start and put under the room's Payload defaults and an agent's own (the same name, the later one wins; an agent can switch one off). On for the agents of the room, off for Clean Room agents (turning either on asks for your password). Servers you already logged in to keep their login on this machine. A server whose name is new at a start is announced in the Downlink and in the banner (names and targets only, dismissable). The page lists names, types and addresses only.
- **Docking page rewritten for Docking 2.** What a task link is, what the other station can and cannot do, hand off, return, recall and accept, chains, missions, cost reports and link caps, knowledge on request, the board and the Outbound view, what leaves your station, and every per-dock rule with its default.

## 0.15.0 (2026-11-23)

Docker Compose needs no settings: `docker compose up -d` and open it from any device on your network by its private IP. Before you update: the new compose.yaml publishes on every interface (0.0.0.0), so set GONOGO_HOST=127.0.0.1 in the .env next to it to keep gonogo on this machine, and make your account before you open it to others. Docker publishes ports past ufw and firewalld, so a host firewall does not hide port 7777; use GONOGO_HOST or a DOCKER-USER rule. If you set GONOGO_DATA before, keep it in that .env, or gonogo starts with a new, empty data folder (it says so in the log). Also: an insecure-setup banner, Docking that works behind the rooms proxy, Clean Room under network_mode host, a DOCKED chip, a shorter hire form, and an Update key that is never unreachable.

- **Docker Compose: the names you reach gonogo by now reach the container.** `compose.yaml` forwards `GONOGO_ALLOWED_HOSTS`, `GONOGO_PUBLIC_URL`, `GONOGO_TRUSTED_PROXY` and `GONOGO_CLIENT_IP_HEADER` from your shell or `.env` (before, only the overlays did, so `GONOGO_ALLOWED_HOSTS` in `.env` was ignored and every name but `localhost` got "forbidden host"; one you do not set stays unset). A browser that gets "forbidden host" now also reads what to set (`GONOGO_ALLOWED_HOSTS`, `--allow-host`, the `.env` and `docker compose up -d`); programs still get exactly `forbidden host`. CI starts the published image with `compose.yaml` and checks an allowed name is answered and another gets 403.
- **Docker Compose: `docker compose up -d` and nothing else.** `GONOGO_DATA` defaults to `./gonogo-data` next to `compose.yaml` (compose run from a UI with no working directory still stops and asks for it, instead of using a folder at `/`), `DOCKER_GID` is gone (the image finds the Docker socket's group when it drops from root, so remove it from your `.env` or leave it: nothing reads it), and the port is published on every interface (`0.0.0.0`) by default: the login with its one-hour setup token is what keeps others out. Set `GONOGO_HOST=127.0.0.1` in `.env` to keep it on the machine. **What changes if you already have a `.env`:** nothing, except that `0.0.0.0` is now the default where you set no `GONOGO_HOST`.
- **A banner for an insecure setup.** Under the top bar, a banner lists what is open in this install (plain http from another computer, a public name with no second factor, an agent that runs without asking, a mounted Docker socket and so on), the most severe first, each with how to close it and a Dismiss that is for good; Dismiss all when there are several. It reads again after any change you make and when you come back to the tab. A key's page and a terminal login see nothing.
- **A "Docked" chip in the room.** The status strip shows which stations this one is connected to ("Docked: lab, ops", "Docked 2" on a phone) with a dot for each, and turns amber with "lab down" when one does not answer. Pressing it opens Docking in Flight Rules. With no station docked there is no chip.
- **Shift+Enter in a reply is a new line.** The reply box under a message (the inbox and the Party Line) sent the message on Shift+Enter. It is now a text box like the Brief box: Enter sends, Shift+Enter makes a new line, and the Enter that confirms an input-method composition sends nothing.
- **Staffing a console starts with three fields.** The staffing form now asks for the engine, a name and the working directory (it starts as the room's Project folder), with a plain line on each. Everything else (role of a seated position, model, effort, Clean Room, worktree, permissions, Payload, keys) is under MORE SETTINGS, folded; it opens by itself for an error, a bypass to confirm, or an agent that already has something set there.
- **Update key when the strip is not there.** With a newer version out, the version key could say the Update key was in the strip under the top bar while the strip was not drawn, so there was nothing to press. The strip and the key now share one rule and one copy of the dismissal.
- **Docking works through the rooms proxy again.** Since 0.10.0 the supervisor dropped every `x-gonogo-` header of a request, including the four a docked station signs its calls with (`x-gonogo-station`, `-timestamp`, `-nonce`, `-signature`). Two installs could pair (the pairing proof is in the body) but every later call (roster, message, hand-off, undock) was refused with "the call is not signed by a docked station", so the dock stayed `down`. The proxy now passes exactly those four headers on `/dock/` and `/uplink/` (a generic webhook's `X-Gonogo-Signature` was dropped the same way); every other `x-gonogo-` header, a forged `x-gonogo-director` or `-actor` included, is still dropped, and nothing changes for the page or a WebSocket. A webhook that sends only `Authorization: Bearer <secret>` still reaches the room without it (the proxy never forwards Authorization): sign it with `X-Gonogo-Signature` instead.
- **Clean Room works with gonogo in `network_mode: host`.** `container:self` is now found by the container id from gonogo's own files (the host name is the host's under host networking), and when that container runs with the host's network the Clean Room is started with `--network host` and `host.docker.internal` on 127.0.0.1. Nothing changes in any other mode.
- **A gonogo answers to its IP address with no configuration.** The front port accepts the IP addresses of the computer and its network as the `Host` (loopback, private, link-local, CGNAT such as Tailscale; names and PUBLIC addresses still need `--allow-host` or `GONOGO_ALLOWED_HOSTS`), so a container or a computer is reached from any device on the network at `http://<its address>:7777`; the login rules by the kind of address are unchanged. The 403 for a name that is not allowed says what to do. The `gonogo ready:` line carries the public address when one is named, and in a container a line on stderr says how to reach it.
- **A banner for an insecure setup.** `GET /api/exposure/findings` lists what is not safe (no login while reachable beyond this machine, plain http on a network address, a public IP address allowed, a public name with no second factor, the Docker socket mounted), each with what to do; the Director's own login can dismiss one for good (`POST /api/exposure/dismiss`), and a new finding shows again.
- **Uplink docs: sign, do not send Bearer.** `X-Gonogo-Signature` is the proof that works behind the supervisor; `Authorization: Bearer` only works when a room is called directly.
- **Fix: the page was told "the log changed" every second while semantic search was off.** After any Mission Log entry was written, the semantic search loop (off by default) sent an empty `log` frame on every tick, for ever, and every open page fetched the log again each time. It now sends one only when it has something to index. This also removes an e2e flake that saw an extra `log` frame.

## 0.14.0 (2026-11-23)

Each room has its own project folder, and gonogo installs itself as a system service (systemd, launchd, OpenRC on glibc). A newcomer is led through the first run: the login comes first, a signed-out or rejected Claude shows as needs you, and Getting started gives copy-paste steps.

- **`gonogo service`: run gonogo under systemd, launchd or OpenRC.** `gonogo service install [--no-start] [--home] [--host] [--port] [--pty-host]` writes a systemd user unit, a macOS LaunchAgent or an OpenRC init script that runs as you, in your home (it pins the paths of node and gonogo and your `PATH`), and starts it at once, with no reboot (`--no-start` only writes the file); `start`, `stop`, `restart`, `status` and `uninstall` complete it. A step that needs root stops with the line to run again with `sudo` and your flags; the service runs as you, never as root. It will not start beside a foreground gonogo that holds the port. Under a service, a reload and the Update key make gonogo exit and the manager starts the next one (`GONOGO_SERVICE`), and `gonogo reload` is allowed in a container that has its own manager. Docs: Run it as a service.
A new install says what to do first: while no login exists the first screen has a "Step one: set up your login" strip that leads to the setup. After the setup, the address gonogo printed (with the key in it) lands on the login page with the line "That address was for the first setup, before a login existed. Sign in with your name and password.", and a room tab that had the key says "This link was for the first setup" with a SIGN IN key, instead of a bare refusal. ## 0.5.2 (2026-11-19)

Lock fixes: a container restart no longer blocks the start with "another gonogo is using …", and two gonogos can no longer share one home by taking over each other's lock.

- **Locks: one rule for every lock that no pid can judge.** A lock is taken over by its pid only when it is of this boot and this pid namespace; a lock of another boot id (a home on a shared disk), another namespace, a machine with no `/proc` (macOS) or the old form (a pid only) is watched for two beats (30 s) and is alive while its file moves; one that has not moved for two beats (as after a reboot) is taken at once. A holder whose lock file was removed puts it back; it stops only when another gonogo made a lock in its place.
- **Fix: a lock left by an earlier container no longer blocks the start.** `server.lock` and `run/supervisor.lock` held only a pid, and after a container restart (pids start again) that number could name another live process, so room main refused with "another gonogo is using …" for minutes. The lock now also holds the boot id and the start time of its process (from `/proc`), and a pid that is alive with a different stamp is taken over. A lock of the old form (a pid only) is taken over when it is older than the container or boot (pid 1). Without `/proc` (macOS) the pid check stands as before. The stamp also holds the pid namespace, and a gonogo touches its lock every 15 s: a lock of another namespace (two containers on one volume, or the host and a container) counts as alive while its file keeps moving, and is taken over only after 30 s without a beat. A gonogo whose lock file no longer carries its own content leaves, so two never run on one home. **Do not run 0.5.0 next to 0.5.1 or later on one home**: 0.5.0 reads only the first line of the lock and takes over a lock it cannot tell from a stale one.

A Missions view from the Patch Panel, the wall's mission block and the brief box; FLIGHT gets the goal when a mission starts, and the Director is told when its last task is done and decides whether to close it. Three tools for agents (`mission_list`; `mission_create` and `mission_update` for the boss). The wall shows the active mission and falls back to the old guess when there is none.
- **Cost.** Propellant can show dollars (an API-equivalent estimate at list prices) with a budget, a chart of the last 14 days and an editable price table (`~/.gonogo/prices.json`, no network). A budget trips Redline like a token limit and warns once at 80 %. New ledger lines keep the model and the token split; older ones show as unpriced.
- **Container.** The image has the `gh` CLI (2.103.3, checksum verified), and the config of `gh` and of `git config --global` lives in `/state/config`, so a login survives a restart. `POST /api/poll/hold` on a poll already on hold answers "the poll is already on hold".
- **Worktrees.** An `Own git worktree` box starts an agent in its own git worktree and branch (`~/.gonogo/worktrees/<name>`, `gonogo/<name>`), for every engine; the remove dialog can delete the worktree and branch, and git keeps unsaved or unmerged work.
- **Default models.** Flight Rules sets a room model for each engine; consoles with no model of their own use it at their next start. The model field says where its value comes from and that a `/model` typed in a console is not kept.
- **Notifications.** A switch in Flight Rules (off by default, per browser) shows a browser notification for a message to you, a T-minus poll that holds or comes out go, and a Relief request, while the tab is hidden or not focused. Clicking it opens the view. The tab title counts what waits, with or without permission.
- **Phone approvals.** A pending permission or hire request can go to your Telegram chat with signed GO and NO-GO buttons (a hire request: NO-GO and Open only), and an agent can start with `--remote-control` to be approved in the Claude app. Chosen in Flight Rules. Late presses do nothing (`needSeq`). Both are new inbox events too.

## 0.1.2 (2026-11-18)

Features from the backlog. Each was tried with the stand-in agent and in Chrome; a real `claude` came into use after this release.

- **Releases.** npm publishing uses trusted publishing (OIDC); the repository holds no npm token.
- **Static fire.** A T-minus poll with a subject: running SIMSUP agents try to break it, RETRO agents write the rollback. A second agent in a position takes the next free name (`guido-2`).
- **Hold and Telemetry.** A Hold key per agent (Claude Code and Gemini CLI) and a timeline of its tool calls (`telemetry.jsonl`, 200 calls per agent).
- **Patch Panel, Flight Rules and Commissioning.** A command bar (Cmd+K or Ctrl+K) that opens any console, view or action, one screen with every setting, and a checklist for an empty room. The views without a key of their own (Party Line, Plot Board, Black Box, Hangar, Recorder) open from the Patch Panel.
- **Party Line.** Messages grouped into conversations, with a reply box.
- **Relief.** FLIGHT can ask to hire an agent with `hire_agent`; only your GO hires it. Limits: `default` or `acceptEdits` only, at most 24 agents, 3 requests waiting, 5 in 10 minutes, 30 minutes to answer.
- **Mass Budget and Star Chart.** REFLECT asks an agent to condense its `memory.md` (gonogo keeps one copy and never writes the file); the Mission Log as a graph. Semantic search is not built: it needs a model gonogo does not ship.
- **Hangar and Recorder.** The files and the git of one agent's folder: a tree with a plain editor (create and save, no delete or rename), and status, diff, log and commit (no push, pull, checkout or reset).
- **Clearance, Pad Check and Rollout.** A model and API keys per agent (`keys.json`, written once, never shown); `gonogo doctor` lists the agent CLIs found and prints the vendor's install command, never runs it; once a day gonogo asks the npm registry for a newer version (turn it off with `GONOGO_UPDATE_CHECK=0` or `--no-update-check`) and `gonogo update` prints the command.
- **Plot Board.** One shared plan (`board.md`): every agent reads it, FLIGHT and you write it, and a write must name the revision it read.
- **Black Box.** An append-only record of the room (hires, stops, polls, Redline trips, plan changes, uplink deliveries, configuration changes) in a git repository in `~/.gonogo/black-box/`, committed by the server in batches. Names and ids only. Without git the room works and the page says so.
- **MCP tools.** `board_read`, `board_write` (boss only) and `hire_agent` (boss only) join the others.
- **Files.** New in the home: `board.md`, `black-box/`, `telemetry.jsonl`, `keys.json`, `rollout.json`. `agents.json` keeps version 1 with new optional fields (`model`, the names of keys): a gonogo older than this one drops them on its next save, while the values stay in `keys.json`.
- **Docs.** Every page opens with its piece of the room, in the room's style, and the pages are shorter. The home page says what go / no-go means.
- **Fix.** The image and CI build with pnpm 12.

## 0.1.1 (2026-11-18)

## 0.1.0 (2026-11-17)

The first release, as the image `ghcr.io/ulm0/gonogo:0.1.0`. Its tag still names the package `gonogo`, so 0.1.0 was not published to npm.

- **Server and room.** One Node process starts each agent as a real `claude` in a pseudo-terminal and shows the terminals, a room of consoles, a wall, the Brief box and go/no-go polls in the browser, on a phone too. FLIGHT is the boss agent. Agents message each other and the Director through MCP tools. A token in the URL guards the page; state lives in `~/.gonogo`. At most 24 agents.
- **Engine Bay.** Gemini CLI, Codex and other CLIs as engines besides Claude Code (not yet tried against a model).
- **Payload.** MCP servers and skill folders per agent.
- **Clean Room.** A Claude Code agent in a Docker container with a copy of its project.
- **Redline.** Stops an agent that loops, hits an error storm or ping-pongs messages.
- **Propellant.** Token budgets per agent and for the room, over 5 hours, a day, a week or a month.
- **Launch Window.** Schedules that send a message on a rule.
- **Uplink.** Webhooks, signed or with a bearer token, delivered to an agent.
- **Relay.** Slack, GitHub, Linear and Telegram in, Slack and Telegram out (never run against the real services).
- **Flight Plan.** A task board shared by you and the agents.
- **Downlink.** An inbox for what agents send to you and for alerts.
- **Mission Log.** A shared memory with search.
- **Livery.** Four themes, and themes an agent designs, checked for contrast.
- **Docking.** Two installations pair, message each other and hand off tasks.
- **Packaging.** The `gonogo` command from a clone or a packed tarball (Node 24 or newer, macOS or Linux with glibc), a Docker image for linux/amd64 and linux/arm64, and the documentation site <https://gonogo.ulm0.com/>.

What was not verified is listed in [What was not verified](https://gonogo.ulm0.com/reference/not-verified.html).
