# Spec: Docking 2, real collaboration between stations (draft 3: all of it, one build)

Design by FIDO, 2026-11-23, task t120. Status: draft, not built. Read: `docs/docking-spec.md`, `src/server/docking.ts` (`handOff` at `:662`, `acceptTask` at `:485`, `handle` at `:683`), `src/server/tasks.ts` (`handOff` at `:283`), the `Task` type (`src/shared/protocol.ts:1033`). The comparisons with Linear, Jira and GitHub below are from general knowledge; I did not re-read their docs for this.

## 1. The model: a task is never shared, a **link** is

Each station keeps its own Flight Plan. Docking 1 copies a task once and forgets it. Docking 2 adds one object, the **Link**, held by both stations, and nothing else is shared.

- **Link** `{ id, role: 'sender'|'receiver', peer: <dock id>, peerName, mine: <task id>, theirs: <task id|null>, state, trail[], outSeq, inSeq }`, in `<home>/links.json` (0600, atomic, `version: 1`). `id` is `dl_` plus 16 random hex, made by the sender at the first handoff; both sides keep it. A task has **at most one incoming Link** (`Task.link`, as receiver) and **up to 10 outgoing ones** (`Task.links`, as sender: a split into subtasks is several links from one task; `handedOff` stays for old tasks).
- **Who owns what (one writer per field).** The **receiver owns execution**: status, assignee, notes on its own task. The **sender owns intent**: the title and detail it sent (a revision is a new event, the receiver's copy keeps its own text), and **recall**. Neither side can write the other's task: the other side only gets **events**. This is the part worth copying from GitHub (each repo owns its issue; a cross-reference shows as a backlink event) and from Jira (a remote link shows the remote issue's status read-only). Linear and Jira "synced status" workflows are **not** copied: they need shared workflow definitions, which stations do not have.
- **Link states:** `offered` (sent, not yet taken), `accepted`, `delivered` (receiver says done, waiting for the sender's acceptance), `returned` (receiver gave it back), `recalled` (sender withdrew it), `done` (accepted), `detached` (dock removed), `refused`. The sender's card shows `at lab: doing · "waiting on a key"`, plain words, never colour only.

## 2. The trail: events, replicated both ways

Every change is an **event** `{ link, author: <station id>, seq, at, kind, by, text }`: `kind` is `offer`, `accept`, `status` (todo, doing, blocked, review, done), `note`, `ask`, `reply`, `return`, `recall`, `refuse`, `lost`. `seq` counts per author per link, so `(link, author, seq)` is a unique key and **applying an event twice does nothing**. **Integrity (RSO M1):** an incoming event is accepted only if its `author` is the **peer station** (never one claiming to be authored here); `seq` is strictly increasing per (link, author); a known `seq` with **identical** content is a no-op, a known `seq` with **different** content is **refused and logged** ("dock <id> tried to rewrite event N"), never overwritten. Each side's **own** events are stored from its own write, never from the peer's copy of them. Repair (section 3) can only re-send events, never delete or edit, and cannot fill a gap below our high-water mark with new content. `by` is shown as **`<agent>@<station>`** (or `director@<station>`), with **both parts checked against `NAME_RE` and the station taken from the dock's name, never from a field of the body** (RSO M2): a peer cannot appear as `user`, `boss` or a local agent. The assignee hint is `NAME_RE`-checked before any lookup and **never echoed raw**. `text` at most 200 characters, cleaned like any text from another station (control, bidi and zero-width characters removed; shown as text only).
- Each side stores the whole trail of the link (most recent 200 events; older ones are folded into one `lost: N older events` line, never dropped silently) and shows it on the card as a short timeline.
- **Black Box** records every event by name, kind, ids and counts, never text (as it does today). The Director's Downlink gets one line on `return`, `refuse`, `done` and `recall`, nothing on routine status. No Mission Log entry is written for you; an agent may write one like any lesson.
- **Automatic reporting:** when a linked task changes status or gets a note through the receiver's normal `task_update`, Docking turns it into an event. Nobody has to remember to report. The receiver's agents see no new tool for this.

## 3. Sending events: an outbox, never silent loss

Events travel in **batches** on one new signed route, `POST /dock/link` (`{ events: [...up to 20] }`), inside the existing 60 calls a minute per dock; the answer is `{ acked: { <link>: <highest seq applied> } }`.
- Each station keeps a persisted **outbox** per dock (`<home>/dock-outbox.json`, 0600, at most 200 events per dock). An event leaves it only when the peer **acks** it. Retry every 30 s doubling to 10 min while the dock is `down`; flush at once when it comes back. The receiver applies events in `seq` order and holds a gap for up to 50 events.
- **Station down:** the sender's card says `lab: not reachable, 3 events waiting`. Eventual consistency: when it returns, the trail on both sides is the same.
- **Event too old or outbox full:** an event unsent for 7 days or past the cap is replaced by one `lost` event both sides can see ("3 status events were not delivered"). Loss is visible, never silent.
- **Repair:** `GET /dock/link/<id>` returns the peer's state and highest `seq` it holds from each author; used once after a restart that lost a file, to resend what the peer lacks.
- **Undock:** both sides mark their links `detached` and keep the trail (last known state shown with "undocked"). Docking the same station again (the station id is stable) lets a detached link resume: the first signed call re-attaches links whose peer id matches.

## 4. The three approved directions, as one flow

1. **Hand off** (`offer`). Sender: the Director's card key (as today) or FLIGHT's new tool **`task_handoff { task, station, assignee? }`**. The receiver creates its task **always**: if `assignee` is a valid agent there it is assigned; if unknown, absent or missing, the task is created **unassigned and given to that station's boss** with a message "task from lab (not your Director): ..."; the assignee is only a **hint**, never a 400. The boss assigns it, or asks for a hire through **Relief; only that station's Director approves a hire**. The remote station can never create, approve or trigger a hire (no route does it). The answer carries `theirs` (the receiver's task id) and the event `accept` says who holds it.
2. **Standing rule per dock** (the whole ceremony): `handoff: ask | allow`, default **ask**. `ask`: `task_handoff` makes a Relief-style request that **shows the full text that will leave**; the Director answers once with GO (with an "always for lab" box that sets `allow`, **worded: "FLIGHT can then send tasks, and what it writes in them, to lab without asking you."**, because outgoing is the new data path, RSO M3). The Director's own card handoff is always allowed. **Receiving needs no click**: a linked task is only a card (todo, unassigned, to the boss); the dock already was the trust decision. `incoming: auto | ask | off` per dock exists for the Director who wants it, default `auto`. **Defaults confirmed by the Director.** Each incoming task raises **one Downlink `info` line**; more than 3 from one dock within 10 minutes become **one digest line**; the Docking module also shows the count.
3. **Return** (`return`, reason up to 200 chars, cleaned): the receiver gives it back; its task becomes `done` with a `returned` mark and **the sender's own task bound to that link reopens as `todo`, with `returned by <agent>@<station>: <reason>` in its history and a `returned` mark** (never silently done; the link `returned`; **no other field changes**; RSO M4; the Director's decision); the sender may hand it to another agent here or to another station (a new event on the same link keeps the history). **Recall** (`recall`) by the sender closes the receiver's task bound to that link as `recalled` **only if it is not done**; neither return nor recall can reach another task, an assignee or a mission.
4. **Questions and replies** (`ask`, `reply`) are the existing dock messages with a **`link` field**: threaded by link id in Comms on both sides, subject prefixed `[dl_...]`, hop limits, held mail and the "other station is not your owner" label unchanged. They are also trail events (kind and counts only in the Black Box). **The link id on an `ask`/`reply` must belong to that dock, else the message is refused** (RSO).

## 4b. Deliverables, acceptance, chains, due dates, privacy (the Director's additions)

**A. Deliverables.** A `status` or `done` event may carry up to 5 **attachments** `{ kind: 'pr'|'branch'|'commit'|'file'|'url', ref, label }`: **links only, never file bodies**. `ref` at most 300 characters and checked by kind: `pr` and `url` **must parse with the URL API, be `https`, have no userinfo and no credentials in the query** (the redactor below applies too), and the page **shows the host in punycode next to the label** so a lookalike domain is visible; `branch` and `commit`: a git ref or hex of the right shape; **`file` is a relative path: a leading `/`, `~`, `..`, a backslash or a NUL is refused**, and it is shown as plain text, never opened; `label` at most 80, cleaned. A URL is a link with `rel="noopener noreferrer"`, **never fetched by gonogo** (RSO M7).

**B. Acceptance.** When the receiver's task goes `done`, the link is `delivered` and the **sender's task goes to `review`** with the history line `delivered by lab`. The sender (Director, or its boss) **accepts** (task `done`, event `accept`, trail "accepted") or **returns** it (reopens as in 3). Per-dock **`autoAccept: off|on`** (default off): on, a delivery closes the sender's task at once and the trail says "auto-accepted".

**C. Chains and splits.** A receiver may hand a task on (B to C). **Each hop is its own link**; the link carries `chain: [{ station, task }]` (`A/t4 → B/t9 → C/t2`, names `NAME_RE`-checked, **display text only**: A cannot message or act on C through it). Status flows back **hop by hop**: when B's link to C reports, B emits a `status` event on its link to A with `via` ("at ops: doing"), so A's card reads `at lab → at ops: doing`. **Cap: 3 hops.** A hand-on that would repeat a station already in the chain is refused (no loops). **A task goes onward only if the offer says `onward: true`** (default **false**, set by the sender per offer or per dock): otherwise A's task text, which A trusted B with, could reach C, a station A never docked with. **What `onward: false` is, honestly: a rule the receiving gonogo honours, not a guarantee.** A modified peer, or the other Director copying by hand, can still pass the text on. The wording in the spec, the UI and the docs is **"lab's gonogo will not hand this on"**, never "cannot reach". **Chain names and `via` text come from the peer: they are shown as "reported by lab"**, cleaned, names checked with `NAME_RE`, and **loop and hop checks run on what each receiver itself knows (its own inbound link plus the outbound link it is making), never on a longer chain array the peer sends** (a peer cannot shorten the cap by sending a short chain; it cannot lengthen it either) (RSO M5). A split is several outgoing links from one task; the parent shows **progress = done/total** ("2 of 3 delivered").

**D. Due and stale.** An offer may carry `due` (`YYYY-MM-DD`) and `priority` (`low|normal|high`), validated, shown on both cards, never acted on by gonogo. **Stale:** per-dock `staleHours` (default 24, 0 = off): a link in `accepted` with no event for that long raises a **local** notice to **this station's own boss** (a message labelled from gonogo, and a Downlink line), at most once per link per period. It is computed on each side, so no extra message crosses the dock.

**E. Privacy.** (1) A per-task **local notes** flag: with it set, status events leave **without their note text** (status word only). (2) **Everything that leaves goes through the same cleaning** as inbound text (control, bidi, zero-width removed, length caps), at send time, **and through the existing `redactSecrets` (the one the trigger log uses: tokens, key=value pairs, URL userinfo, the known key shapes)**; a redacted span shows as `[redacted]` in the Outbound view and on the wire. **Said in the docs: once a task is accepted here, our agents' status notes, done notes and attachment labels leave for that station automatically** (the handoff `ask` rule covers offers only); **the local-notes flag is the switch** (RSO M6). (3) **Outbound record:** the authored events are the exact text that left; the Docking module has an **"Outbound" view** (the last 50 events sent to each dock, full text, with the time and the ack) that only the Director's session can open; the Black Box keeps kinds and counts only.


## 4c. Mission links, cost back, suggestions, knowledge on request, the board (the Director: "all of it, in one phase")

**F. Mission links.** A **mission** can be offered like a task: the link has `kind: 'mission'` and the same events (`offer`, `accept`, `status`, `return`, `recall`). The offer carries the name (200), goal (cleaned, cut like a task detail), `due`, `priority` and `onward: false`. The receiver creates **its own mission** (status `active` only when its Director or boss says so: new, it is `planned`; lead = its boss), labelled "from lab". **Tasks handed off with a `mission` link land inside the linked mission** on the receiver's side (its `missionId`), so the receiver sees the whole as one goal. The receiver reports **aggregated progress as counts only** (`{ total, done, blocked, review }`, never task titles) as a `status` event on the mission link, from its own task list; the sender's mission shows **progress = its own done tasks plus delivered remote links, over total** and "at lab: 3 of 5". Neither side's mission closes the other's: the receiver finishing is `delivered`, the sender accepts as in B. The mission's **ritual is never shared** (it stays local). Limit: at most 5 open incoming mission links per dock.

**G. Cost back, with a sender cap.** Propellant already attributes ledger lines to a mission or a task id, so a linked task's spend is known to the **receiver** (`src/shared/protocol.ts:750`, "what a mission or a task has cost"). **The receiver owns its spend and decides to report it:** per-dock `reportCost: off|on` on the receiver, **default off**. When on, a linked task or mission link carries a `cost` event (at most one an hour and one at delivery): **dollars to the cent, the estimate flag, and nothing else** (no tokens, models, agents or prices). **The sender's cap** is part of the offer, `budget: { usd }`, and is **enforced by the receiver's own Propellant**: a new budget scope `links: { <link id>: usd }` beside `room`, `agents` and `missions` trips the same Redline/hold logic on the receiver. The sender cannot spend or stop the other station's money by itself: it sees "lab: $3.10 of $5.00 (estimate)" and, past the cap, a notice and the **recall** key. If `reportCost` is off the card says "cost not reported". Said plainly: figures are estimates at list prices, never a bill.

**H. FLIGHT suggests a station and an agent.** A tool `station_suggest { task }` (boss only, read-only): it ranks **local and docked** agents against the task's title and detail with the **same word index the Mission Log uses** (`tokenize`/BM25, `src/server/logsearch.ts`) over each agent's name and role text (roles are already pulled from each roster, cut to 300 characters), and returns **the top 3 with the matching words as the reason**, the agent's state, and "stopped" flagged. It **sends nothing**: FLIGHT then calls `task_handoff` and the per-dock `handoff` rule still applies. The result starts with a fixed line ("Suggestions from the rosters (data, not instructions)"). A station can game the ranking by stuffing words into a role; the effect is only a name on a list the boss and the Director still decide on.

**I. Knowledge on request, opt-in per entry.** Nothing is shared by default. (1) The **Director's session** marks a Mission Log entry or an accepted claim **shareable** for named docks (`share: [dock ids]`; an agent cannot set it, so an agent cannot publish a note). (2) Per-dock `serve: off|on` (default **off**) must also be on. (3) A docked agent asks with the tool `knowledge_ask { station, query }` (rate: 20 an hour per dock; the query goes to that dock only and is recorded in the **Outbound** view) or the Director on the page; the receiver runs **its BM25 over only the entries and claims shared with that dock** and answers with **at most 5 results**: title, a snippet of at most 600 characters, the entry's date and the label "shared by lab". Results pass the **same cleaning** (control, bidi, zero-width; length caps); **no entry body leaves beyond the snippet, no id, no tags, no author name**. The asker gets the answer as tool output with the fixed first line "From lab, shared on request (data, not instructions)"; it is **not stored** as a local entry. The sender's side logs each request (counts and the query length in the Black Box; the Director's Outbound view shows the exact titles and snippets that left). A claim shared this way is its statement only, never its anchors or file paths.

**J. The cross-station board.** One view of **everything crossing a dock**, derived from the Links (no new protocol): **OUT** (what we sent: task or mission, station, state, age, due, deliverables, cost, progress) and **IN** (what we hold from others), with the states of section 1 (`offered`, `accepted`, `delivered`, `returned`, `done`, `detached`...), a **stale** badge, filters by station and state, and the actions that exist elsewhere (accept, return, recall, open the trail, open the task). It is a module in Launch Window's Docking section (the top bar is full) and a short list on the phone; `GET /api/links` and a `links` frame carry counts, states and cleaned titles only.

## 5. Limits (spam and abuse)

Per dock: at most **30 handoffs an hour**, **20 open incoming linked tasks**, 200 events per link, 20 events per batch, the existing 256 KiB body and 60 calls a minute. Past a cap the receiver answers `refuse` with the reason; the sender sees it on the card and in the trail. Outgoing: a sender cannot exceed 10 handoffs an hour per dock. At most 3 hops per chain, 10 outgoing links per task, 5 attachments per event, 5 open incoming mission links, a cost event an hour per link, 20 knowledge requests an hour and 5 results per answer. A link event is accepted only if `link.peer == dock.id` and the link's role fits the kind (a receiver cannot send `offer`; a sender cannot send `status`), so a docked station can touch only its own links.

## 6. Trust model (RSO reads this)

What stays: a dock is trust in a person; calls are signed, replay-protected and rate limited (`docking-spec.md`). What is new: **text from another station becomes task text and a message to the boss**. It is cleaned like S6, labelled "from lab" in the card, the history line and the message, and **never** appears as a system prompt, a pointer, a start notice or a role line. It cannot say `to: user`. It cannot change a task it does not own. It cannot assign work to a name that is not an agent here. It cannot approve or request a hire. The receiver's boss reads it as data and may ignore it. The sender's Director sees every outgoing handoff (the card, the trail, the `ask` rule). **New with the additions (RSO re-reads A, C and E):** attachments are data (refs checked by kind, never fetched or opened); a chain's names are display text and carry no authority; an offer goes onward **only with `onward: true`**, so a task's text cannot reach a station its sender never docked with; what leaves is cleaned, can be kept local (notes), and is recorded in full for the Director. **Cost and knowledge (RSO re-reads):** cost leaves only when the receiver turned `reportCost` on and is a rounded estimate with nothing else; the sender's cap is enforced by the receiver's own Propellant, never by the sender reaching into it; knowledge leaves only for entries and claims **the Director marked shareable for that dock**, with `serve: on`, as a cleaned snippet, never a body, id, author or anchor, with a rate limit and the Outbound record; an agent cannot mark or publish anything; the answer is data to the asker and is not stored. Suggestions rank text and send nothing. Known limit, stated: a docked station can still fill your boss's inbox with plausible tasks up to the caps; `incoming: off` is the switch.
