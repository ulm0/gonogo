# Spec: Publishing gonogo to the internet (draft, 0.5.0)

Design by FIDO, 2026-11-18, task t56b. Status: draft, not built; depends on `docs/login-spec.md` (PR 1 at least). Provider facts read on 2026-11-18 from each vendor's docs (what a page did **not** say is listed as such). Nothing was run; the recipes in `docs/https.md` also say they were not run.

## What gonogo checks today
Bind `127.0.0.1` by default; `403 forbidden host` for a `Host` that is not loopback, the bind address or an `--allow-host` name; a browser `Origin` must equal `Host`; the browser token for `/api` and `/ws`; `/hook` and `/mcp` take agent tokens and are meant for loopback (a Clean Room uses `host.docker.internal`). `docs/https.md` recommends keeping the page off the public name and exposing only `/uplink/*` and `/dock/*`. No TLS, no notion of "exposed", no trusted-proxy handling: a forwarded address is not used anywhere.

## Rules gonogo enforces (new)

1. **Two kinds of public name.** `--allow-host name` is a **page host**; `--allow-host name:hooks` is a **hooks host** that serves only `/uplink/*` and `/dock/*` (404 for everything else, so the page never exists there). Existing `GONOGO_ALLOWED_HOSTS` entries stay page hosts. This keeps the safest existing pattern (webhooks on a public name, the page private) and gives it a name.
2. **Login before any page host that is not loopback.** A request to `/`, `/api` or `/ws` whose `Host` is not a loopback name is answered only when the account of `docs/login-spec.md` exists and has a second factor or a passkey. Until then it gets one page, "set up the login from the host", which accepts the **setup token** (so an existing LAN user is not locked out: they enter their token once and create the account). `/hook` and `/mcp` answer **404 to any non-loopback Host** except `host.docker.internal` (a test pins it).
3. **Start-up refusal.** `--allow-host <public name>` (or an env entry), or a non-loopback `--host` **outside a container**, without the login set up: gonogo refuses to start with one message that says what to run. In a container the wildcard bind is normal, so the bind is not the signal there; the Host rule above is.
4. **A public URL and https.** `--public-url https://gonogo.example.com` (also `GONOGO_PUBLIC_URL`) says where the page is. Public names (not loopback, not private) **require an `https` public URL**: gonogo does not guess from forwarded headers whether TLS happened, it takes the Director's word and refuses a page host with no https URL. The URL sets the cookie's `Secure`, the WebAuthn origin and rp id, the links in notifications and Docking pairing codes, and the webhook addresses shown for Uplink and Relay. A **private** name (RFC 1918, ULA, link-local, 100.64/10 tailnet addresses, single-label names, `.local`, `.lan`, `.home.arpa`) may stay plain http with the login and a visible "not encrypted" warning.
5. **Trusted proxy and client address.** Rate limits use the socket peer. `--trusted-proxy loopback` (or a CIDR) lets gonogo read `--client-ip-header` (`x-forwarded-for` or `cf-connecting-ip`) **only from those peers**, so a stranger cannot pick the bucket; a tunnel sees every client as `127.0.0.1`, so without this setting the global bucket does the work. The login's "local credential" rule (no forwarding header, loopback Host) is unaffected by it.
6. **WebSocket keepalive.** The page already pings; the doc says that Cloudflare closes idle sockets after an unstated time and that a ping interval under that is needed (the builder checks the current interval is short enough; not verified).
7. **Always off the internet:** the Docker socket, `/hook`, `/mcp`, Hangar writes without step-up (login spec), and `GONOGO_UPDATE_HOOK`.

## `gonogo expose <provider>`: print and write, never run

**Option A (pick): print and write config, then check.** `gonogo expose tailscale|cloudflare|caddy|ngrok [--public-url ...] [--write]` prints the exact commands and the settings gonogo needs (`--allow-host`, `--public-url`, `--trusted-proxy`) and, with `--write`, writes **files only** into `<home>/expose/` (a `Caddyfile`, a cloudflared `config.yml` skeleton, a compose override snippet, an nginx block). It runs no tunnel, installs nothing, holds no provider credential and touches no network setting: the same rule as `gonogo update` and Rollout ("gonogo never runs an installer").
**`gonogo expose check`** runs on the host after the Director has done the provider steps: it refuses if login is not set up, fetches `<public-url>` from the host (one request to the Director's own URL), and reports whether TLS answers, `/api/state` returns **401 with no credential**, `/hook/x/Stop` and `/mcp` return 404, a WebSocket upgrade to `/ws` answers 401 (so the path and upgrade work), the `Host` the proxy forwards is the public one, and the response has the CSP of the login spec. It prints pass/fail lines and changes nothing.
**Option B: gonogo starts and supervises the tunnel** (`cloudflared`, `tailscale`, `ngrok`, `caddy`). One command for the user, but gonogo would manage a third-party process that needs the vendor's login and token, version drift, restarts and a binary on the host, in the project that has said it never installs anything; and an `expose` bug would silently publish the page. Rejected.

## Docs per provider (`docs/expose/<provider>.md`), each with a "tried / not tried" line
Order recommended: **1 Tailscale Serve** (private; the phone joins the tailnet; https for free; no public surface), **2 Cloudflare Tunnel, named tunnel** (public, outbound-only, no open port; Cloudflare Access can sit in front as a second layer, but the app must still log in), **3 Caddy on a VPS or home server with ports 80/443** (full control), **4 Tailscale Funnel** (public, `*.ts.net` name, bandwidth limits), **5 ngrok**. **Quick Tunnels are for testing only** and unsuitable here: the name changes on every run, so `--allow-host`, the public URL and passkeys (rp id) break. Each page: the exact config, what to put in `--allow-host` and `--public-url`, whether the Host is preserved, and the `expose check` output expected. `docs/https.md` is replaced by this set and keeps its webhook-only recipe.

## Scope of the PR (after login PR 1)
`--public-url`, `--allow-host name[:hooks]`, private-name classification, the Host/login gate and the start-up refusal, `--trusted-proxy` and `--client-ip-header`, `gonogo expose <provider> [--write]` and `expose check`, the docs set and `docs/https.md` rewrite, Flight Rules shows "exposed to: <names>" and "login: ready/not". About 600 lines with tests. **Left out:** running tunnels, certificates, DNS, IP allow-lists, per-provider auto-detection of headers, mTLS.

## Tests
Gate table (Host x login state x path: loopback, private, public; page host, hooks host); `/hook` and `/mcp` 404 for public Host, still fine for `127.0.0.1` and `host.docker.internal`; start-up refusals (public allow-host without login, non-loopback bind outside a container, https required for a public name, plain http allowed for a private name with the warning); forwarded address ignored unless the peer is trusted; `--allow-host x:hooks` serves only the two webhook prefixes; `expose` prints and writes files with mode 0600 and nothing else (no process spawned: a test fails the spawn); `expose check` against a fake server for each pass and fail line. Not testable here: a real tunnel or certificate.

## For RSO
Whether the private-name classification can be abused (a DNS name that resolves to a private address from outside, rebinding with an allowed name); whether `:hooks` hosts could ever reach the page through a path trick or a different `Host` casing; the claim that a tunnel hides nothing the login does not already cover.
