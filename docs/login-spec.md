# Spec: Login for the Director (draft, 0.5.0)

Design by FIDO, 2026-11-18, task t56a. Status: draft, not built. Read from `web.ts` (token, Host and Origin checks, WebSocket subprotocol), `docs/reference/security.md`, `docs/https.md`; web facts read on 2026-11-18 from MDN (WebAuthn, `PublicKeyCredentialCreationOptions`) and the Node docs (`crypto.argon2`). Nothing was run. **RSO must review this before anyone builds it** (list at the end).

## Why the token is not enough once the page leaves the machine

Today one static secret, the browser token, opens every `/api` route and `/ws`. It never expires, has no second factor, is kept in the browser and lives in the URL fragment of a bookmark. What it opens is not "a dashboard": it **hires an agent with a custom command** (a shell command as the owner), starts `bypassPermissions` agents, types into every terminal, writes any file in an agent's folder (Hangar), commits (Recorder), answers permission dialogs and can start Docker updates. **A leaked token is a shell on the host.** On localhost that was acceptable; behind a tunnel it is not. So: a login with a session that expires, a second factor, and a stronger check for the dangerous actions.

## What is unchanged
Agent tokens (`/hook`, `/mcp`); `/uplink/<id>` (its own secret or signature) so phone approvals through Telegram and Relay webhooks keep working; `/dock/*` (signed requests); the Host and Origin checks. None of these ever took the browser token, so none changes.

## Design

- **One account.** `<home>/auth.json` (0600, atomic write, damaged file kept as `.bad` and login refused until `gonogo auth reset`): `{ version, user: { name }, password, totp?, recovery?, passkeys[], keys[], sessions[] }`. One Director. The user name is a label (default `director`) so a password manager fills the form; a wrong name and a wrong password give the **same answer in the same time**, so nothing says which was wrong.
- **Password.** `argon2id` through Node's own `crypto.argon2` (added in Node v24.7.0 per the Node docs: parameters `memory` in KiB, `passes`, `parallelism`, `nonce` of at least 16 random bytes, `tagLength`); no dependency. `engines` says `>=24`, so a Node 24.0 to 24.6 falls back to `scrypt` (`crypto.scrypt`, stored with its parameters, upgraded to argon2id at the next successful login). Cost parameters: the **current OWASP Password Storage cheat-sheet minimum** for argon2id, checked by the builder when writing (not copied from memory here); parameters are stored per hash so they can rise. Length at least 12, no composition rules, no hint. Comparison with `timingSafeEqual`.
- **Rate limits.** Per client address (the socket's peer, or the forwarded address **only** when `--trusted-proxy` names the proxy; never an unchecked header) and one global bucket: failures wait 1, 2, 4 ... seconds up to 15 minutes; a global cap of 20 failures in 10 minutes slows everyone, the Director too. **No permanent lockout** (the only account must not be lockable by a stranger): the answer to guessing is delay, a Downlink event `redline` ("12 failed logins from 203.0.113.9 in 10 min") and the always-open way back: **`gonogo auth reset` run on the host** (filesystem access to the home is the admin boundary, as for every other file) removes the password, MFA and sessions and prints a new setup token.
- **MFA, TOTP.** RFC 6238, SHA-1, 6 digits, 30 s, a window of one step either side, the last accepted step stored so a code works once. The secret is shown once as an `otpauth://` URI and text (a QR is drawn by the page from the URI with a small vendored encoder, or only text: builder's choice). **Recovery codes:** 10 single-use codes of 10 characters from an unambiguous alphabet, stored hashed, regenerated on demand (which voids the old ones). Enabling MFA needs one valid code first. MFA is **on by default for any exposed instance** (see the expose spec: exposure refuses without a second factor *or* a passkey).
- **Passkeys (WebAuthn).** What is true, from MDN: the API is available **only in secure contexts (HTTPS)**; `rp.id` must equal the origin's effective domain or a domain suffix of it, and the credential works only with the rp id it was made for; discoverable credentials are what passkeys are. MDN does not say whether an IP address is a valid rp id, and the spec wording is "a valid domain": **treat an IP address as unsupported** (not verified in a browser). Consequences, said in the page: passkeys need **a name and https** (a tunnel hostname, a Tailscale `*.ts.net` name, a Caddy name); on `http://192.168.x.x` or an IP they are not offered and password plus TOTP is used; `localhost` is a secure context in browsers and may be tried for development (not verified here). The rp id is **fixed at first registration** and stored; a passkey made for `a.example.com` does not work at `b.example.com`, so changing the public name means registering again (the password stays). Library: verify `none` attestation and ES256/RS256/EdDSA assertions with **`@simplewebauthn/server`** (MIT; the builder checks maintenance and license before adding the one new dependency) rather than hand-written COSE parsing; if the Director refuses a dependency, the fallback is own code limited to `none` attestation and ES256, about 200 lines, and a second reviewer. A passkey with user verification counts as password plus second factor in one step.
- **Sessions.** After password and MFA (or a passkey) the server makes 32 random bytes, keeps only their SHA-256 with creation time, last use, address and user agent, and sets the cookie `__Host-gonogo` (`Secure; HttpOnly; SameSite=Strict; Path=/`; the `__Host-` prefix needs https). On plain `http://localhost` and plain-http LAN use (no TLS) the cookie is `gonogo-session` without `Secure`, the login page shows a **"this connection is not encrypted" warning**, and a non-loopback plain-http login is allowed only when not exposed. Idle timeout 12 h, absolute 30 days, "this device" list in Flight Rules with REVOKE and LOG OUT EVERYWHERE; a password change revokes all sessions.
- **CSRF and cross-site WebSocket.** Today REST uses a header token, so there is no CSRF; cookies change that. Rules for cookie-authenticated requests: `SameSite=Strict`; the existing Origin equals Host check, **plus an Origin header required** on every non-GET (a missing Origin with a cookie is 403, unlike today's header-token clients); the WebSocket upgrade keeps its Origin check (this is the cross-site WebSocket hijack defence) and takes the cookie instead of the subprotocol token.
- **Step-up for what is dangerous.** A session older than 5 minutes since its last password or passkey check must re-confirm (password, TOTP or passkey) for: hiring with a custom command, `bypassPermissions` or `auto`; Hangar writes; Recorder commits; changing credentials, MFA, API keys or Features; Docker self-update; docking. This keeps a stolen cookie from becoming a shell without the second factor. Built in the last PR so the first PRs stay small.
- **Setup and migration from the token.** At the first start after upgrade nothing changes for a local user: the page opens as before with the token. The **setup screen** (create the account) is reachable only with the existing token, over loopback or an exposed instance: `#token=` becomes the **setup token**, printed as today. Once an account exists:
  - The browser stops accepting `#token=` as a login (it only opens setup if the account was reset).
  - The token file stays as the **local credential**: valid only for a request whose peer is loopback, whose `Host` is a loopback name and which carries **no forwarding header** (`X-Forwarded-*`, `Forwarded`, `CF-Connecting-IP`, `Tailscale-*`, `Via`). This keeps `gonogo tui`, `gonogo` CLI commands and local scripts working with no change. A tunnel connects from loopback, so the Host and the forwarding headers decide, not the peer address alone; a proxy that rewrites Host to `127.0.0.1` and strips forwarding headers would pass as local, which is why `gonogo expose` configures providers to keep the public Host and why exposure is refused while the instance cannot tell.
  - **API keys** for remote scripts and a remote TUI: `gonogo auth key add <name>` (or the page) prints a key once; stored hashed with name, creation and last use; sent as `Authorization: Bearer`; each can be revoked; they carry the same power as a session **without the step-up**, so they are listed as dangerous, shown with last use, and off until the Director makes one.
- **Rooms.** `docs/rooms-spec.md`: the **supervisor** owns this login and the sessions; it swaps in each room's own token toward the child; children keep the token as a loopback-only credential (they are not reachable except through the supervisor).
- **Threat model, in short.** (1) Guessing and stuffing: argon2id, delay, global cap, MFA. (2) Stolen cookie: HttpOnly, short idle, device list, step-up. (3) XSS: gonogo has `X-Frame-Options: DENY` but **no Content-Security-Policy** today; the PR adds a strict one (`default-src 'self'`, no inline script, `frame-ancestors 'none'`), because a script in the page now could ride the session. (4) CSRF and WebSocket hijack: above. (5) Host-header tricks: allowed hosts stay. (6) Brute force of API keys: 256-bit random, constant-time compare. (7) Enumeration: single account, same answer and time. (8) Log hygiene: no password, code, cookie, key or session id in any log or event. (9) **A running agent is not in this model**: agents run as the owner and can read `auth.json` and every other file (`docs/reference/security.md`); the login defends against the network, not against `bypassPermissions` on the host; Clean Room is the only boundary there. (10) The reset path trusts whoever has the host: stated.

## Options

1. **Own login, built from Node's crypto, one small dependency for WebAuthn (pick).** Matches a single-person product: no outside identity provider to run or trust, works offline, everything in one file.
2. **Delegate to the tunnel or proxy** (Cloudflare Access, Tailscale identity, ngrok OAuth, a Caddy `forward_auth`) and have gonogo trust an identity header. Less code, and good for people who already have an identity provider; but gonogo would then trust headers that anyone on the path can forge unless it knows the proxy, it breaks for plain LAN, and "internet exposure is safe" would depend on a service the user may not have set up. Kept as an **extra**, not the base: `--trust-header` is left out of the first PRs and listed as the later way to say "this proxy has already authenticated".

## Scope: four PRs

1. **Password and sessions**: `auth.json`, argon2id/scrypt, setup screen, login page, cookie session, device list, rate limits, the local-credential rule, API keys, CSP, CSRF rules, `gonogo auth reset`, Flight Rules block; the token keeps working locally. About 900 lines with tests.
2. **TOTP and recovery codes.** About 300 lines.
3. **Passkeys** (the dependency decision). About 350 lines.
4. **Step-up** on the dangerous routes. About 250 lines.
**Left out:** several users or roles, password reset by email, SSO/OIDC, remember-me beyond 30 days, hardware-token attestation, `--trust-header`.

## Tests
Hash and verify (both algorithms, upgrade on login); same answer and timing for a wrong name and a wrong password; backoff and the global cap with a fake clock; **a spoofed `X-Forwarded-For` does not change the bucket unless the proxy is trusted**; TOTP window and replay; recovery codes once only; session creation, idle and absolute expiry, revoke, password change revokes; cookie flags on https and on loopback http; non-GET without Origin is 403 with a cookie and fine with a Bearer API key; WebSocket with a foreign Origin refused; the local credential is refused when Host is public, when any forwarding header is present, and when the peer is not loopback; `/hook`, `/mcp`, `/uplink`, `/dock` still answer as before with the login on; step-up needed and satisfied; CSP header on the page and no inline script left; no secret in logs (a test greps the log output of a full login). Not testable here: a real WebAuthn authenticator (use the library's test vectors and say so), a real tunnel.

## For RSO (please break these)
(a) the local-credential rule behind a proxy that rewrites Host; (b) the setup screen as a takeover window on an exposed fresh instance (answer: exposure refuses until an account exists, and setup needs the token, which only the host has); (c) `gonogo auth reset` and the agent-as-same-user problem (an agent can run it); (d) session fixation and cookie scope with rooms and `/r/<id>/`; (e) the IP-address rp id claim, to be tried in real browsers; (f) whether step-up is enough or the dangerous routes need MFA every time.
