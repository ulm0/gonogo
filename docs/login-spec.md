# Spec: Login for the Director (draft 5, 0.5.0)

Design by FIDO, 2026-11-18, task t56a, revised after RSO's review (Mission Log l17, R1 to R11). Status: **PR 1 and PR 2 built** (see "As built" at the end); passkeys are not built. Read from `web.ts` (token, Host and Origin checks, WebSocket subprotocol), `docs/reference/security.md`, `docs/https.md`, `roomproxy.ts`; web facts read on 2026-11-18 from MDN (WebAuthn, `PublicKeyCredentialCreationOptions`) and the Node docs (`crypto.argon2`). Nothing was run.

> **Single mode (docs/single-mode-spec.md, t58):** `gonogo` always runs the supervisor, so the login lives only in the supervisor: one account, setup, session store and rate limiter, the Host normalizer at the front port, and one cookie with `Path=/` for `/` and `/r/<id>/`. Every child is reached only through its `run/api.sock` (R8 is the baseline, not an add-on) and accepts no token on TCP. Wherever this spec says "gonogo" for the process that checks logins, read "the supervisor". Login PR 1 comes after the two single-mode PRs.

## Why the token is not enough once the page leaves the machine

One static secret, the browser token, opens every `/api` route and `/ws`. It never expires, has no second factor, and has been printed in compose logs, bookmarks and shell history. What it opens is a shell on the host: hire an agent with a **custom command**, start `bypassPermissions` agents, **type into every terminal**, write files in an agent's folder (Hangar), commit (Recorder), answer permission dialogs, start Docker updates. On localhost that was acceptable; behind a tunnel it is not.

**A logged-in session is shell-equivalent, and the page says so** (Flight Rules, the login screen's first-run text and the docs). Through a console or a message to an agent a session can make a `bypassPermissions` agent run anything. Step-up (below) raises the cost of the quickest routes and of changing the account; it **does not** make a stolen session safe. What protects a session is: a second factor at login, short lifetimes on public names, device list and revoke, alerts, and not exposing the page when the Director does not need to.

## What is unchanged
Agent tokens (`/hook`, `/mcp`); `/uplink/<id>` (own secret or signature); `/dock/*` (signed); the Host and Origin checks. None ever took the browser token. **Telegram phone approvals stay a second authentication path that bypasses the login** (a signed button answers a permission or a Relief request); they are limited to approvals, and the threat model says so.

## Design

- **One account.** `<home>/auth.json` (0600, atomic write; a damaged file is kept as `.bad` and page logins are refused until `gonogo auth reset`): `{ version, user, password, totp?, recovery?, passkeys[], keys[], sessions[], devices, serverKey }`. One Director. The user name is a label (default `director`) so a password manager fills the form. A wrong name **hashes a dummy password** and answers the same message in the same time as a wrong password.
- **Password.** `argon2id` through Node's `crypto.argon2` (added in v24.7.0 per the Node docs; `memory` in KiB, `passes`, `parallelism`, `nonce` of 16 random bytes at least, `tagLength`); `engines` says `>=24`, so Node 24.0 to 24.6 falls back to `crypto.scrypt`, stored with its parameters and upgraded at the next login. Cost: the **current OWASP Password Storage cheat-sheet minimum** for argon2id, taken by the builder when writing, stored per hash so it can rise. Length at least 12, no composition rules. `timingSafeEqual`. **Changing the password, or turning MFA off, needs the current password, the current second factor and step-up.**
- **Rate limits and no lockout (R6).** Failures wait 1, 2, 4 ... seconds up to 15 minutes **per bucket**. Buckets: one per client address (the socket peer, or the forwarded address only from `--trusted-proxy`), one per **known device**, and one global bucket for **unknown devices** only. A *known device* carries the signed cookie `gonogo-device` (HMAC with `serverKey`, HttpOnly, Secure when possible, 1 year) set after a successful **full** login (password and second factor, or a passkey); it gets its own bucket and **is not slowed by the global cap**, so a stranger's guessing, or a whole tunnel's clients sharing one address, cannot keep the Director out. **Passkey assertions are exempt from backoff** (not guessable; still verified). **TOTP and recovery-code failures count in the same buckets** as password failures. 20 failures in 10 minutes from unknown devices raise an alert (R4). There is **no permanent lockout**. The way back is `gonogo auth reset` on the host.
- **MFA, TOTP.** RFC 6238, SHA-1, 6 digits, 30 s, one step either side, the last accepted step stored (a code works once). The secret is shown once as an `otpauth://` URI and text. **Recovery codes:** 10 single-use codes of 10 characters from an unambiguous alphabet, stored hashed, regenerated on demand (the old ones die). Enabling needs one valid code first. **On plain http to a non-loopback host, TOTP is required every login** (a LAN sniffer gets the password and a cookie); passkeys count as both factors. Exposure requires a second factor or a passkey (`docs/expose-spec.md`).
- **Passkeys (WebAuthn).** From MDN: only in **secure contexts (HTTPS)**; `rp.id` must equal the origin's effective domain or a domain suffix; a credential works only with the rp id it was made for. MDN does not say whether an IP is a valid rp id; RSO confirms WebAuthn requires a valid domain and browsers refuse an IP address as rp id, and that `localhost` is accepted by Chrome and Firefox. So: **IP address unsupported** (still to be tried in real browsers before the docs claim it), `localhost` allowed for development. Passkeys need **a name and https**; on `http://192.168.x.x` password plus TOTP is used. The rp id is fixed at first registration; a passkey for `a.example.com` does not work at `b.example.com` (the password stays). Library: **`@simplewebauthn/server`** (MIT; the builder checks maintenance and license; the Director decides the one new dependency); fallback: own code for `none` attestation and ES256, about 200 lines, with a second reviewer. A passkey with user verification is password plus second factor in one step.
- **Sessions (R5).** After a full login the server makes 32 random bytes, keeps only their SHA-256 with creation, last use, address, user agent and the device id, and sets `__Host-gonogo` (`Secure; HttpOnly; SameSite=Strict; Path=/`). On plain http (loopback or private LAN) the cookie is `gonogo-session` without `Secure`, with a visible "not encrypted" warning. **Lifetimes: on a public name idle 2 h and absolute 7 days; on a loopback or private name idle 12 h and absolute 30 days.** The id is minted by the server after auth, never taken from the client, and **re-minted after step-up**. "Last use" is refreshed by an API call or by input to a console (at most once a minute); terminal output does not keep a session alive. Device list in Flight Rules with REVOKE and LOG OUT EVERYWHERE; a password change revokes every session except the current one.
- **WebSockets are bound to their session (R5).** The `/ws` upgrade takes the cookie, records the session id on the socket, **re-checks idle and absolute expiry every minute** (terminal sockets live for hours), and **closes the socket** when that session is revoked, logged out, expired, or when the password changes. A socket never outlives its session.
- **CSRF and cross-site WebSocket.** `SameSite=Strict`; the Origin equals Host check; **an Origin is required on every non-GET** when a cookie authenticates the request (a missing Origin is 403, unlike today's header-token clients); the WebSocket upgrade keeps its Origin check.
- **Step-up, widened (R5).** A session more than 5 minutes past its last password or passkey check must re-confirm (password, TOTP or passkey) for: hiring with a custom command, `bypassPermissions` or `auto`; **editing an agent's mode, command or role**; **the permissions editor**; **Uplink, Relay and Docking secrets**; **Clearance keys**; **creating an API key**; **Features**; Hangar writes; Recorder commits; changing the password, MFA, passkeys or sessions; Docker self-update; docking. **Not behind step-up, and shell-equivalent anyway:** typing into a console, messages to agents, GO on a permission dialog, starting or restarting an existing `bypassPermissions` agent. This list is stated plainly in the page: step-up is a speed bump for the quick routes, not a wall.
- **Tamper alarm (RSO).** An agent outside a Clean Room does not need `reset`: it can write `auth.json` directly (add a session hash or an API key whose secret it knows, read `serverKey` and forge device cookies) or reset, finish setup on loopback and log in remotely with the account it made. Hardening `reset` buys nothing; the cheap control is to make the change loud. **After each of its own writes the server stores a hash of `auth.json`; on every request (rate-limited to one check a second) and on a 5-second timer it hashes the file on disk, and when it differs it raises a `redline` Downlink event plus Relay ("auth.json changed outside gonogo"), ends every session, API key and push subscription it did not make itself (it reloads the file and keeps only entries it can match to its own record), and refuses new remote logins until the Director confirms on the host. **The confirmation is never a bare prompt** (an agent can reach the TUI over `api.sock` and the page on loopback, so it could plant a password hash and confirm itself): **it takes the Director's password and second factor, checked against the server's in-memory copy of the account from before the change, never against the file it just reloaded.** The server also **keeps `serverKey` in memory**, so device cookies forged with a planted key stay invalid.** `gonogo auth reset` is the one allowed outside writer, and **"reset" changes nothing but the alert's label**: a reset-labelled write is always treated as ending in **the empty account plus the new setup token**, and any session, key, passkey, device or password found in that file is dropped, so an agent cannot forge the reset label to smuggle an entry in.
- **Exposed means any non-Clean-Room agent can open the door.** Said in the docs and in Flight Rules: **when exposed, any agent that does not run in a Clean Room can open the remote door** (tamper above, or its own reset and setup), so run agents in a **Clean Room on exposed instances**. Flight Rules shows a warning while exposure is on and such an agent exists, naming the agents.
- **Alerts (R4).** A Downlink `redline` event, forwarded by Relay when configured, for: `gonogo auth reset`; the **first login from a new device**; a new API key; MFA turned off; a password change; the failure cap above. The event names the address and device, never a secret.
- **API keys (R7).** `gonogo auth key add <name> [--scope read|act|full] [--expires 90d]` (or the page, with step-up) prints a key once; stored hashed with name, scope, creation, **expiry (default 90 days)** and last use **with the address**. Scopes: **read** (state, lists), **act** (read plus messages, answers, hold/resume), **full** (opt-in, everything a session can do except account changes). **A key is refused from a public Host unless it was made with `--remote`.** A Bearer key never carries step-up, so `full` keys are listed as dangerous with their last use.
- **Setup, the token and the local door.**
  1. **R1: the old browser token dies at account creation.** Creating the account **deletes the token file and makes no replacement**. The old token (in compose logs, bookmarks, history) stops opening anything. **Only a fresh install that has never had an account** keeps today's behaviour until its first setup (token works over TCP, nothing is exposed: `docs/expose-spec.md` refuses exposure until an account exists). **Once an account has existed, "no account exists" never brings a TCP token back**: after `gonogo auth reset` the only credential is the setup token, and it works only on a loopback or private Host (R3); the old token file is not recreated, and the unix socket stays the local door. The server records "an account was created" in `auth.json`'s tombstone (kept by `reset`) so it can tell a fresh install from a reset one.
  2. **R1: a separate setup token.** `<home>/setup-token` (0600): 32 random bytes, **single use, valid 1 hour**, made when no account exists, **regenerated by `gonogo auth reset`**, and printed once by `gonogo` at start when no account exists. The old token is accepted by the setup screen only until the account is created, as a convenience for existing users, and is then gone as above.
  3. **R3: setup, and setup after a reset, are answered only on a loopback or private Host.** A public page host answers "login is not set up: open gonogo from this machine or your LAN" and **never accepts a setup token**. A stolen setup token is therefore useless from the internet.
  4. **R2: the local door is a unix socket.** Once an account exists, `gonogo tui`, `gonogo` CLI commands and local scripts talk to **`<home>/run/api.sock`** (directory 0700, socket 0600; the same HTTP API and `/ws` over a unix socket; the file permissions are the credential, as for the pty host's socket today). **No token is accepted on TCP**, for any Host, so a proxy that rewrites Host or drops forwarding headers (nginx's default server, `cloudflared` with `httpHostHeader`, `socat`, `ssh -L`) gains nothing. `curl --unix-socket` covers scripts. A remote TUI or script uses an API key. If a platform cannot make the socket, the **minimum** is: refuse a request that carries an Origin header, `gonogo expose check` sends the *old local token* through the public URL and requires 401, and every generated proxy config sets `X-Forwarded-For`.
  5. **(c) the agent-reads-the-setup-token problem.** Agents outside a Clean Room run as the owner; one can run `gonogo auth reset` and read the setup token (from its pty or the file). **The design does not try to hide it** (it cannot, from the same user); it makes it **worthless remotely**: R3 means the token only works on loopback or a private Host, `reset` fires the R4 alert, ends every session, key and push subscription, and **turns public page hosts into "login not set up" pages**, so the worst remote outcome is the Director locked out of the public name until they reset from the host, not a takeover. `auth reset` prints "setup token written to `<home>/setup-token`" and **does not print the token**, so it does not land in an agent's pty or a log; the server notices the changed `auth.json` on the next request.
- **Rooms (R8).** The supervisor owns the login and the sessions. **It reaches each child through the child's own `<home>/run/api.sock`** (no token on TCP anywhere: a child has no TCP credential at all, so a Host-rewriting proxy or a stray connection aimed at a child's port gets nothing); the `roomproxy.ts` token swap is replaced by the socket connection. Room pages share its origin, so: **the proxy strips `Set-Cookie` from every room response** (a room cannot overwrite or fix `__Host-gonogo`; it already drops `Cookie` toward rooms), and **the CSP applies to `/r/<id>/` pages and the room list**, since an XSS in one room would ride the session for all.
- **Threat model, in short.** (1) Guessing and stuffing: argon2id, delays per bucket, MFA, alerts. (2) Stolen cookie: HttpOnly, short public lifetimes, device list, revoke, alerts, step-up on the quick routes; **but a stolen session is shell-equivalent** (said above). (3) XSS: strict CSP (`default-src 'self'`, no inline script, `frame-ancestors 'none'`; none today), on every page including rooms. (4) CSRF and WebSocket hijack: above. (5) Host-header tricks: allowed hosts and the Host normalizer of the expose spec. (6) API keys: 256-bit, constant-time compare, expiry, scope, no public Host by default. (7) Enumeration: dummy hash, same answer and time. (8) Logs: no password, code, cookie, key, setup token or session id in any log, event or `ps`-visible argument. (9) **A running agent outside a Clean Room is not in this model**: it runs as the owner and can read and edit `auth.json` or run `auth reset`; the tamper alarm makes that loud but cannot stop it, the login defends against the network, and **Clean Room is the only boundary**, so exposed instances should run agents in one. **Known limit:** the tamper alarm compares against a record kept in memory, so a change to `auth.json` made **while gonogo is stopped** is not detected: the next start loads the planted file. A cheap partial net, left for a later PR: alert the first time a session or API key is used from an address it has never been seen with, so a planted cookie used from outside still makes noise. (10) Telegram approvals bypass the login by design: approvals only. (11) A TLS-terminating tunnel sees everything (`docs/expose-spec.md`).

## Options

1. **Own login, from Node's crypto, one small dependency for WebAuthn (pick).** One person, nothing to run or trust outside, works offline, one file.
2. **Delegate to the tunnel or proxy** (Cloudflare Access, Tailscale identity, ngrok OAuth, `forward_auth`) and trust an identity header. Less code and fine for someone with an identity provider, but gonogo would trust headers anyone on the path could forge unless it knew the proxy, it does not work on a plain LAN, and exposure safety would depend on a service the user may not have set up. A later extra, `--trust-header`, for "this proxy has authenticated".

## Scope: four PRs

1. **Password and sessions**: `auth.json`, hashing, **setup screen with the separate setup token (R1, R3)**, login page, cookie session with the R5 lifetimes and **WebSocket binding**, device cookie and the R6 buckets, device list, **unix-socket local door and TUI/CLI switch (R2)**, token deletion at account creation, API keys with expiry and scope (R7), alerts (R4), CSP, CSRF rules, `gonogo auth reset`, rooms' `Set-Cookie` strip (R8), Flight Rules block. About 1200 lines with tests.
2. **TOTP and recovery codes.** About 300 lines.
3. **Passkeys** (the dependency decision). About 350 lines.
4. **Step-up** on the widened list. About 300 lines.
**Left out:** several users or roles, password reset by email, SSO/OIDC, remember-me beyond the lifetimes, hardware attestation, `--trust-header`.

## Tests
Hash and verify (both algorithms, upgrade on login; dummy hash for a wrong name, timing within a margin); **bucket behaviour: a flood of unknown-device failures does not slow a known device or a passkey login; TOTP failures count; a spoofed `X-Forwarded-For` changes nothing without a trusted proxy**; setup token single use, 1 h expiry, regenerated by reset, **refused on a public Host and accepted on loopback and private Hosts**; old token dead after account creation (TCP, with and without Origin, with a rewritten Host and no forwarding header); the unix socket 0600 in a 0700 directory serves `/api` and `/ws`, the TUI uses it; reset ends sessions, API keys and push subscriptions, does not print the token, flips public hosts to "not set up", and fires the alert; each alert type; session lifetimes by Host class; the **WebSocket closes on revoke, logout, password change and expiry**, and terminal input refreshes last use at most once a minute; cookie flags on https and loopback http; non-GET without Origin is 403 with a cookie; a foreign-Origin WebSocket is refused; API key scope, expiry and public-Host refusal; `/hook`, `/mcp`, `/uplink`, `/dock` unchanged; step-up needed and satisfied on each listed route and **not** required on the listed shell-equivalent routes (so the page text stays true); session id changes after step-up; CSP header on the page, rooms and list, no inline script; room responses lose `Set-Cookie`; no secret in logs (a test greps the log of a full login, reset and key creation). Tamper alarm: a write to `auth.json` by another process (a planted session hash, a planted API key, a changed `serverKey`) raises the alert within 5 s, drops the unmatched entries and blocks remote logins until confirmed on loopback; the server's own writes and `auth reset` do not false-alarm (the reset one is labelled); after a reset **no TCP token works** and the setup token is refused on a public Host; the Flight Rules warning appears only with exposure on and a non-Clean-Room agent present; a room child answers nothing with a token on its TCP port and the supervisor reaches it by socket. Tamper confirm: planting a password hash then confirming through the TUI over `api.sock` or the loopback page **fails** (the check runs against the in-memory record from before the change); a device cookie forged with a planted `serverKey` is invalid; a write labelled as a reset that contains a session, key, passkey, device or password is reduced to the empty account plus the setup token. Not testable here: a real authenticator (use the library's vectors), a real tunnel.

## RSO's questions, answered
(a) The local credential behind a Host-rewriting proxy: removed (R2: unix socket, no token on TCP). (b) Setup as a takeover window: separate single-use 1 h token, rotated away from the old one (R1), and local-or-private only (R3). (c) `auth reset` by an agent: cannot be prevented, made harmless remotely and loud (above). (d) Session fixation and rooms: id minted after auth and after step-up; `Set-Cookie` stripped; CSP on rooms (R8). (e) IP rp id: unsupported, to be tried in browsers. (f) Step-up not enough: agreed, stated plainly, list widened, lifetimes shortened on public names, sockets bound (R5).

## As built (PR 1, GUIDO)

What differs from the draft, and what was left for PR 2:

- **Two sockets, two names.** The supervisor's local door is `<home>/run/api.sock` (directory 0700, socket 0600). Each room answers on its own `<room home>/run/room.sock`: room `main`'s home is the root home, so it could not also be `api.sock`. A room's page has **no TCP credential**: the room started by the supervisor refuses every browser token on TCP, `run/room-token` is gone (a leftover file is removed), and the supervisor reaches the room only over `room.sock`. Agents keep their own tokens on the room's loopback port (`/hook`, `/mcp`).
- **Split.** PR 1 is everything above except TOTP, recovery codes and step-up (PR 2) and passkeys. The session is as strong as the password alone until PR 2; the page says so.
- **Setup token.** Made at the first start with no account (`<home>/setup-token`, 0600), printed once on the start-up output, valid one hour from the file's modification time, single use, deleted at account creation. While gonogo runs, an expired file is renewed silently (not printed) so the setup page is never stuck. `gonogo auth reset` writes a new one and does not print it.
- **Fresh install versus reset.** `auth.json` holds a tombstone once an account has existed. With no file and no tombstone (fresh install) the old `<home>/token` still works on TCP and the setup screen accepts it; with a tombstone no browser token exists, and `gonogo token rotate` refuses. Account creation deletes `<home>/token`.
- **Buckets.** Per address (the socket peer; `X-Forwarded-For` only from an address given with `--trusted-proxy` or `GONOGO_TRUSTED_PROXY`), one global for unknown devices, one per known device (the signed `gonogo-device` cookie). A known device is held only by its own bucket (a tunnel's clients share one address and must not lock the Director out). Attempts turned away by a wait count as failures for the alert (20 in 10 minutes from unknown devices, once per window).
- **Cookies.** Decided by the Host's class: a loopback or private name gets `gonogo-session` (no `Secure`, lifetime 12 h idle and 30 days), a public name `__Host-gonogo` (`Secure`, 2 h and 7 days). The id is minted at login. Input to a console refreshes the session at most once a minute; a WebSocket is checked every minute and closed on revoke, logout, expiry, password change, reset and tamper. Input is recognised as a data frame from the browser (a pong is not).
- **CSP.** Rooms' pages and the room list get `default-src 'self'; script-src 'self'; frame-ancestors 'none'`, with `style-src 'unsafe-inline'` (the terminal writes styles); the login and setup pages are plain forms with no script and a stricter policy. Not tried in a real browser.
- **Scopes of API keys.** `read`: GET except terminal output and key routes; `act`: read plus `POST /api/messages`, an agent's hold, resume and answer, a poll's hold or abort, a Relief GO or NO-GO; `full`: everything except `/api/auth`. The rooms list is changed by a `full` key only. Keys are held to a public name only when made with `--remote`.
- **Alerts** reach room `main`'s Downlink as `redline` events (and Relay) over the pipe the supervisor shares with it (`gonogo-alert "<text>"` on the room's standard input), waiting for `main` when it is not up yet.
- **Tamper alarm.** The in-memory account is the truth: on a change the unmatched sessions, keys and devices go, the file is written back from memory, and remote logins are paused until `POST /api/auth/confirm` (or `gonogo auth confirm`) with the password, checked against the memory copy. A write labelled `reset: true` is reduced to the empty account (setup token already written by the CLI). **Known limit as in the spec:** a change made while gonogo is stopped is not seen; and an amend of the file at the moment the server writes it is a race the next check settles.
- **After review (RSO, RETRO).** Every decision of the proxy (the login, a key's scope, the agents' routes) is made on the path decoded once, and the room is sent the path built again from those segments, so `/%61pi/state` is `/api/state` for both or for neither. The class of a request is the wider of its Host's and its address's, and public when a forwarding header came from a peer that is not a trusted proxy. A socket may be opened by a session, the local socket, the old token or a `full` key only, and is bound to its session or key. A save of `auth.json` first looks at whether the file changed under it. The setup is guarded against two at once. The hash parameters of a file are clamped (a planted one cannot ask for gigabytes). A prefix names one session or key or none. Alerts carry no control character or markup from the browser's name. On a tamper the file is written back from the account in memory (what gonogo made stays; what the outside write added is gone).
- **Not built:** passkeys; the alert for a session or key used from a never-seen address.

### PR 2: the second factor and step-up

- **TOTP.** RFC 6238, HMAC-SHA1, six digits, 30 s, one step either side, the last accepted step stored so a code works once (tried against the RFC's vectors). The secret (20 random bytes) is shown once as text (base32) and as an `otpauth://` address; **a first valid code switches it on**, and then ten recovery codes are made and shown once (ten characters from an alphabet without 0, O, 1, I, L; stored as SHA-256; typed in any case, with spaces or dashes). A recovery code works once and raises an alert.
- **Login in two steps.** A right password with TOTP on answers "second factor" and a single-use token valid five minutes (a hidden field in the form, `pending` in JSON); `POST /api/auth/second` takes the code or a recovery code. **A right password does not clear the failure buckets**, so a code cannot be guessed round after round by giving the password again; TOTP and recovery failures count in the same buckets as password failures; five wrong codes end that login.
- **A public name needs a second factor.** With none on, a password alone is refused there ("this address needs a second factor"; turn it on from this machine or your network first). On a loopback or private name a password alone still works, with the warning about plain http. **Reading of "TOTP is required every login on plain http":** gonogo never lets a known device skip the code, so once TOTP is on it is asked at every login whatever the address; the stricter reading (refuse a LAN login that has no TOTP) was not taken because it would lock out a headless install that is only used on its own network. Say if the stricter one is wanted.
- **Turning it off, and new recovery codes,** need the current password **and** a current code (or recovery code): a stolen session alone cannot. Both raise an alert. `gonogo auth reset` takes the second factor away with the account.
- **Step-up.** A session carries when its password (and code) was last checked. After five minutes the changes of the spec's list are refused with a 403 `stepUp` until `POST /api/auth/stepup` {password, code} confirms: hiring with a command of its own or an unattended mode (the body decides, so the proxy reads it), editing an agent (an ALLOW-list: only name, position, autostart, coauthor, model and effort are free; any other field, including one a later version adds, asks), hiring outside a Clean Room, with remote control or with keys of its own, the room's permissions, Features, Uplink, Relay and Docking, the keys of an engine, Hangar writes, Recorder commits, a Docker update, and the account's own changes (password, keys, sessions, turning a second factor on). **The id of the session is minted again** on step-up (the old cookie value dies); its sockets move to the new id and stay open. Not behind it, as the spec says: typing into a console, a message, a GO on a permission dialog, hold, resume, start and restart of an existing agent. A key, the local socket and the old token are not sessions and are not asked.
- **Page.** A SECOND FACTOR block in Flight Rules (turn on, recovery codes, turn off) and a CONFIRM IT IS YOU dialog that the page opens by itself when a change is refused for this reason, then repeats the change.
