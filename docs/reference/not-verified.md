# What was not verified

Update this list when these are run.

- **Docker.** Built and run on 2026-11-17 with Docker 29.9 in a Lima VM (linux/arm64, Debian bookworm, glibc): the build-time checks pass as uid 1000 (`claude` 2.1.325, `gonogo --version`, a real pty), the image is about 1.06 GB, the `HEALTHCHECK` reports healthy, the port is reachable from the host, and with the stand-in agent mounted in the container the hooks, pointers, `read_messages`, a reply, a custom agent, a T-minus poll to GO and Max Q all worked. `docker stop` with two agents running took 0.4 s with exit code 0, and a restart on the same named volumes kept the roster with its positions and the custom agent. Open: linux/amd64, a real `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` in the container (seed mode with a real `claude`), a bind-mounted `/projects` and its ownership, and the `safe.directory` entries. With the docker CLI added (Docker 29.9.1 client, checked by `docker --version` at every build) the image is about 1.13 GB; the build also needed `docs/brand` back in the build context (`.dockerignore`), where the app's logo lives.
- **Linux.** Only inside the container above (arm64, glibc). Not run: Linux as a host, amd64, a real `claude` on Linux.
- **Sign-in in a container.** The recipe behind seed mode was tried by hand on a Mac with fake credentials only. A real `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` in a container was never used, and neither was `apiKeyHelper` with a real key.
- **A real `claude`, end to end.** `scripts/smoke-real.mjs` (a script of the repository, not of the package) ran with `--spend` against claude 2.1.325 (macOS arm64, model haiku, host mode, seed mode off). It showed that `claude doctor` accepts the generated settings, that a pointer typed into an idle agent is confirmed and the mail is read with `read_messages`, that mail for a working agent is handed over by the Stop hook and the interactive terminal continues the turn, that a permission prompt shows as needs you and clears once allowed, that `NO_PROXY` keeps hook and tool traffic off a proxy, that the first-start argv with `--system-prompt-snapshot off` is accepted, and that a T-minus poll reaches an agent, which answers with `go_nogo` (go), the poll reads GO and FLIGHT is told. Still open: whether `permissions.deny` and `crossSessionInbound` take effect (doctor does not flag them), whether the role text is applied on a first start, the environment of `apiKeyHelper` (seed mode only), other startup dialogs, and that Esc twice clears Claude Code's input box (its documentation says so). [`docs/contract.md`](https://github.com/ulm0/gonogo/blob/main/docs/contract.md) section 15 has the numbers. It ran again at the final check of the roadmap round against claude 2.1.326 (haiku): every step passed, in about 45 s, and Propellant counted about 28k tokens for one agent. The smoke does not touch any feature of that round: no real model has used an Engine Bay engine, a payload, a Clean Room, a schedule, an uplink, the Flight Plan, Downlink, Mission Log, Livery or Relay tools, or a docked station.
- **Positions, T-minus, Max Q, custom agents, the room and the wall.** Tested with the stand-in agent, and the browser was driven in Chrome only: 1440 x 900, 1024 x 768 and a 500 px window (the 390 px layout by DOM measurement only). A real `claude` has answered one poll with `go_nogo` (go); a no-go, hold, abort and Max Q were not run with a real `claude`. A custom agent was run in the end-to-end tests as a small Node command and in the browser as a shell loop; no full-screen program (`htop`, an editor) was tried. Firefox, Safari and screen readers were not tried.
- **The `auto` permission mode.** A real `claude` 2.1.325 was started in `auto` on the owner's account without a prompt: it showed `auto mode on` and no extra dialog. Not verified: a turn in `auto` through gonogo, and what claude does on an account or model that cannot use it.
- **Engine Bay.** No engine other than Claude Code was run against a model. Gemini CLI 0.59.0 was installed but not signed in: its adapter follows its `--help` and its bundled source (`docs/facts/gemini.md`); the hook shim was run against a local server only. pi 1.5.2 was checked by its `--help` (`docs/facts/pi.md`). Codex, opencode, Kimi, Copilot, Qwen, Grok, Crush and Cursor Agent were not installed: their flags and files come from their documentation. The hub's rules for them were tested with fake hooks and output counters. With a real Gemini CLI none of this was seen: the shim's hooks reaching gonogo, the AfterAgent block handing over mail, BeforeAgent confirming a typed pointer (and Enter right after a bracketed paste submitting it), Enter and Escape on its confirmation dialog, its sign-in and trust dialogs, and its first hook arriving within the 5 s startup timer (if it does not, the console shows needs you until the first hook). Whether each engine's terminal turns on bracketed paste is not known; gonogo types no pointer otherwise, so such an agent would get no mail. Gemini's stop-block guard never trips, because BeforeAgent resets the count; every block hands over real mail, so it cannot loop on its own. Engines without the gonogo tools (pi, Qwen, Grok, Crush, Cursor Agent) still get `GONOGO_TOKEN` in their environment (their own token, revoked when they exit). gonogo needs `claude` on `PATH` to start, because FLIGHT is always Claude Code. The Engine select of the hire form was opened in Chrome at 1440 px and in the 390 px phone emulation at the final check (named, no overflow); not with a screen reader.
- **Payload.** Tested with the stand-in agent, plus these checks against the installed `claude` 2.1.325 without a model: `claude plugin validate` accepts the plugin the launcher builds (and says a `--plugin-dir` session follows its symlinks) and a skills folder, and `claude mcp list` connected to a local server written in the same shape (command, args and env). Not run: a model using a payload tool or skill, the permission prompt of a payload tool, the skill's name as Claude Code shows it, a remote (http or sse) server, and a payload entry through `--mcp-config` itself. The PAYLOAD fold was opened at the final check in Chrome at 1440 px and in the 390 px phone emulation (no overflow, every field named), and a console was hired with a payload server, which reached its `mcp.json`; the server was not started by a model. `${NAME}` expansion in payload env and header values is from Claude Code's docs and was not tried. Gemini CLI was not signed in (its settings schema was read from the bundle); Kimi CLI's file shape is from its docs. Codex, opencode and Copilot take no payload (a shortcut in the spec).
- **Clean Room.** Tested with a fake `docker` and real `git`: the arguments, the worktree and the branch, the files the launcher writes, the Host rule, and a hire through the real server in which the stand-in agent runs as if in the container and reaches gonogo by `host.docker.internal` (the stand-in maps the name to this machine). Never run against real Docker (the host `docker` CLI here fails on a keychain error, and real Docker only runs inside a Lima VM): not seen are the mounts, the user, `--entrypoint`, the name resolving, a user with no passwd entry in the image, a real `claude` starting in the container, the stop of the container, and above all whether Claude Code accepts hooks at the address `host.docker.internal` leads to (its bundle blocks private ranges). Also not seen: whether the server is reachable from a container on a Linux bridge with the default `--host 127.0.0.1` (it is not expected to be; `--host 0.0.0.0` is needed there) and Docker Desktop forwarding the name to loopback (from Docker's docs only); the default image `gonogo` built locally for this; a container left behind by a server that was killed; Propellant does not count a Clean Room agent. **Run once with real Docker, gonogo in a container** (2026-11-17, Lima VM, Docker 29.9.1, linux/arm64): the image built from this repository as `ghcr.io/ulm0/gonogo`, `compose.yaml` started with an override for a free name, port and data folder and with the stand-in agent as `GONOGO_AGENT_CMD`. Seen: the docker CLI in gonogo's container talks to the host daemon through the socket as uid 1000 with the socket's group; a hire with the Clean Room box made the worktree and the branch and started `gonogo-ana-<hash>` on the host's Docker with `--network container:<gonogo>`, `--user 1000:1000`, `--entrypoint node`, the worktree, its read-only `.git` and the agent's folder mounted at their same paths (the agent started in the worktree's subfolder, as uid 1000); the hook and MCP URLs were `http://127.0.0.1:7777` (changed at review to `host.docker.internal`, see below); a message went `queued`, `delivered`, `read` (the stand-in called `read_messages` over MCP) and the console went `idle`, `working`, `idle` from its hooks; a stop removed the container, and a restart started a new one on the same worktree. A second gonogo container without the same-path mount refused the start with the `not mounted ... from the same path` text. Rerun at review the same day (a copy of the stand-in agent whose URL check also accepts that name, `docker compose` 5.1.4 with an override for name, port, data folder and agent command): the hook and MCP URLs are `http://host.docker.internal:7777`, the name came from gonogo's hosts file (`extra_hosts`) shared through `--network container:`, the console went `idle`, `working`, `idle` and the message was `read` over MCP; from inside the Clean Room `/api/state` and `/` by that name answered 403 `forbidden host`; a gonogo recreated without `extra_hosts` refused the start with `host.docker.internal names nothing in the container ...`. Not seen there: a real `claude` in the Clean Room (hooks to a name that resolves to loopback should be allowed by Claude Code's rules, not tried), `host-gateway` (the gonogo-on-the-host path, still never run against real Docker), Docker Desktop, linux/amd64, rootless Docker, a gonogo container recreated under a running console. The box was seen unticked in the hire form at 1440 px and in the 390 px phone emulation at the final check; the chip was not seen, since no Clean Room agent ran.
- **Launch Window.** The rule parser and the scheduler are tested on a fake clock (including a skipped and a repeated hour in New York and a 29 February), the routes with a fake store, and a real server with the stand-in agent: a schedule was created, run now, read by the agent, edited and deleted. Never watched: the timer across a real minute boundary, a real sleep of the machine or a clock change, a real `claude` getting a scheduled message. The page was opened in Chrome at 1280 px, in a 500 px window and in Chrome's 390 px phone emulation (no overflow); not in Firefox or Safari, and not with a screen reader. At the final check a schedule was made and run in the 390 px emulation. A fire time that a DST change skips does not fire that day: in America/Santiago the clock skips 00:00 in September, so `0 0 * * *` misses that day. A scheduled message to FLIGHT replaces the MISSION of the wall.
- **Uplink.** The store is tested on a fake clock (signatures and bearer, the same 404 for unknown and disabled, the rate limit, the cut, the file and its recovery), the routes with a fake store (Host, Origin, methods, 413, status codes), and a real server with the stand-in agent: a signed post, a bearer post, a body that is not JSON, another Host, test, rotate, off, a recipient that is gone and delete. A running server was also posted to with `curl` using `openssl` signatures. Never run behind a real reverse proxy (the nginx and Caddy lines are not tried), never from a real GitHub or another real sender, never with a real `claude` reading a delivery. The page was opened in Chrome at 1280 px and in the 390 px phone emulation (no overflow); the Rotate and Delete questions were not opened, and the Copy keys were not pressed. At the final check the form was opened at 390 px, an uplink made there and posted to with `curl` (a correct signature got 202 and the delivery showed in the card, a wrong one 401). Not in Firefox or Safari, and not with a screen reader. Not watched: the saved deliveries across a real restart, the rate limit across a real minute. Not measured: the nginx rate-limit lines and the cost of a flood of failed proofs (a 256 KiB hash each). Accepted: an unknown id answers 404 before the HMAC runs, so timing can tell whether an id exists (ids are not secret); a record that `load()` skips (for example a kind from a later version after a downgrade) is dropped with its secret at the next save, with a warning.
- **Flight Plan.** The store is tested on a fake clock with a fake send (the history lines, the assignment message from the Director and from an agent, a refusal of the hub, the limits, the dropping of old `done` tasks, the file and its recovery), the routes and the three tools with a fake store (the agent comes from the token, the cut of a long list), and a real server with the stand-in agent: the Director made a task for one agent, that agent moved it and made another for a second agent with the tools, and the file was mode 0600. Never run with a real `claude`: whether the model reads the one line of the role text, calls the tools and moves a task it was given is not known, and neither is a Gemini CLI or other engine using them. The page was opened in Chrome at 1280 px and in the 390 px phone emulation (no overflow, keys of at least 44 px): the keyboard follows a moved card, the form shows its error, a task was made from it and the Remove question was answered; those clicks were made by script, not by hand. Not in Firefox or Safari, not with a screen reader, and not with a board of hundreds of cards. At the final check a task was made, moved and handed to an agent in the 390 px emulation, and the agent moved it to review and blocked another over MCP. Known limits: the whole list goes in every frame and snapshot, so a board at its limits nears the 4 MB socket buffer; a task keeps its assignee's name, so it does not follow a renamed console. The counts on the top-bar key are an `aria-label` on a plain span, which Chrome reads into the key's name and other screen readers may not.
- **Downlink.** The store is tested on a fake clock (the items, the cuts and limits, read, archive and read all, the file and its recovery, the first run), the routes with a fake store, the hooks in the hub (a Redline trip, each T-minus result once), Launch Window, Uplink (more than 3 refused requests in 10 minutes, one line for each window) and Flight Plan with a fake `notify`, and a real server with the stand-in agent: a message from an agent, a T-minus abort and a task an agent blocked landed in the inbox, the three routes and the frames worked, and the file was mode 0600. The page was opened in Chrome at 1280 px and in the 390 px phone emulation against that server (no overflow, keys of at least 44 px, the six keys of the phone bar fit): `j`, `k`, `e` and `r`, a reply sent from a row, and the inbox kept across a restart; those keys were pressed by script, not by hand. Never run with a real `claude`: whether an agent writes to `user` when it should is the model's choice. Not in Firefox or Safari, not with a screen reader, not with hundreds of items, not between 700 and 999 px, and `prefers-reduced-motion` was not tried by hand. An Uplink event, a failed Launch Window fire and a Redline trip were tested on a fake clock or through the hub harness, not seen in a real server run. Known limits: every frame carries the whole inbox (about 700 KB at the limits), and after a restart unread mail is found again only among the newest 1000 log records.
- **Mission Log.** The index is tested on its own (ranking by title, tag, rarity, length and repetition, ties, replacing and removing, snippets), the store with a temporary folder and a fake clock (the files and their modes, the limits, who may change what, the disk refusing, a restart, skipped files, ids not given twice), the routes and the three tools with a fake store (the author comes from the token, the cap of 20), and a real server with the stand-in agent: two agents wrote, searched, read and were refused, the Director used every route, the frame carried titles only, and the files were mode 0600. Never run with a real `claude`: whether the model searches the log before work and writes findings worth keeping is not known, and neither is a Gemini CLI or other engine using the tools. The ranking constants were chosen, not tuned on a real log. The page was opened in Chrome at 1280 px and in the 390 px phone emulation against that server (no overflow, keys of at least 44 px, the seven keys of the phone bar fit, the top bar on one line at 1280 px): a search, an entry opened, an edit with its errors, a new entry, a delete with its question, an entry written and one removed from outside while the page was up; those clicks were made by script, not by hand. Not in Firefox or Safari, not with a screen reader, and not with hundreds of entries. Known limits: two writers at once means the last write wins (the form does not warn when an agent rewrites the open entry), a hand edit of a file is seen only after a restart, and an id above `l999999` is not handled. Entries are text a model may follow, like messages: not a channel to trust from an untrusted agent, and not a place for secrets.
- **Relay.** The four proofs are tested against the examples in the documentation of GitHub (`It's a Secret to Everybody`) and Slack (the `v0` example, and its five minute rule), RFC 4231 (the HMAC) and a Telegram token compared as it is; the summaries of each service with payloads written from their documentation; the store, the retries (a 5xx, a 429 with `Retry-After`, a timeout, a refusal that is not tried again), the queue, the token that never reaches a log or a note, and the map of replies with a fake `fetch`; the routes with a fake store; and a real server with the stand-in agent and a fake `fetch` (scenario 28 of the end-to-end tests: signed deliveries of the four kinds, a message to you posted to both targets, a Slack thread reply and a Telegram reply that reached the agent that wrote, a T-minus result forwarded, what is not chosen not sent). A running server was also posted to with `curl` and an `openssl` signature. **Never run against a real Slack, GitHub, Linear or Telegram**: no app, bot or webhook was made, so the shape of a real payload, the replies of `chat.postMessage` and `sendMessage`, Slack's check of the Request URL, a real retry and the menus the steps name (they are from the documentation as remembered, and Linear's URL being editable after the webhook is made is assumed) are not verified. The page was opened in Chrome at 1280 px and in the 390 px phone emulation against a server with the stand-in agent (no overflow, keys of at least 44 px; the forms and their errors, an uplink made for GitHub and one for Slack with its pasted secret, a ping that showed in the card); those keys were pressed by script, and TEST was not pressed against a saved target. Not in Firefox or Safari, not with a screen reader, not behind a real reverse proxy. Known limits: Telegram updates are not deduplicated by `update_id` (Telegram resends only without a 2xx, and gonogo answers at once), and a Slack event is marked handled even when the hub then refuses it (the recipient is gone), so Slack's retry is ignored.
- **Livery.** The colour reader and the contrast check are tested against known values (black on white is 21:1, `#777` on white 4.48:1, `oklch(0.628 0.2577 29.23)` is `#ff0000`) and every livery that ships is checked, and a test keeps Instrument equal to the CSS. The store is tested with a temporary folder (the files and their modes, the limits, a replace, skipped files, a deleted chosen livery), the routes and the tool with a fake store, the page helpers (the xterm theme, the copy kept in the browser) as plain functions, and a real server with the stand-in agent (scenario 29: a refused livery, a saved one, the frames, the Downlink item, the choice, a design request reaching the agent, the files at mode 0600). Never run with a real `claude`: whether a model designs a livery that passes the check from a line of text is not known, and neither is an engine other than Claude Code calling the tool. The page was opened in Chrome at 1280 px and in the 390 px phone emulation against a server with the stand-in agent: the four liveries were applied; Night Shift (the Livery view and the room at 1280 px) and High Contrast (the room at 1280 px, the Livery view at 390 px) were looked at, the terminal repainted in each, and the logo turned on the dark one; after a reload the page had the chosen livery at the first look (the copy in the browser or the server's answer, not told apart); the design box and the delete question worked, an agent's livery appeared and the Downlink counted it; those clicks were made by script, not by hand. No overflow at 390 px, keys of at least 44 px, the top bar on one line at 1280 px. At the final check every view was opened in each of the four liveries at 1440 px and in the 390 px phone emulation, with schedules, an uplink, tasks, inbox items and log entries on screen, and a script measured the rendered text against its background: nothing under 4.5:1. That scan covered no error message, open question, hover or focus state, and an `oklch` colour outside sRGB is clipped per channel in the check where a browser maps it more gently. If removing a custom livery fails on disk after `livery.json` moved back to the default, no livery frame goes out until the next state. `theme-color` was only read as an attribute: no phone's browser bar was looked at. Not in Firefox or Safari, not with a screen reader, not behind a reverse proxy with a Content-Security-Policy.
- **Docking.** The module is tested with two copies of itself wired through a fake `fetch` (the pairing and its refusals, the signatures, replay, expiry, the rate limit, the roster, a message each way, undock, handoff), the routes with a fake module, the hub with a fake link (hops, the limits, Redline's ping-pong, the restart), and two real servers with the stand-in agent on loopback (a pairing over real HTTP, a message each way with its hops, a task handed off, refused calls made by hand, undock). The page was opened in Chrome (a 500 px window, the narrowest Chrome gives; nothing overflowed and every key was at least 44 px tall) against two real servers: the module, the Pair form, a hand-off that moved the card to DONE. At the final check the module, a code and the Pair form were opened in the 390 px phone emulation (no overflow, keys of at least 44 px). Never run between two machines, behind a real reverse proxy or over HTTPS, with a real `claude` reading a message from another station (what it does with one is not known), in Firefox or Safari, with a screen reader, or with the Copy keys. The roster pull every 30 s was tested on a fake timer only. Known limits: codes and seen nonces live in memory, so a call replayed within 5 minutes across a restart is accepted once; if the other station accepts a hand-off and the local task then fails to move, the copy over there stays; a queued message to a station is marked undelivered at a restart with the generic note that it went to the user.
- **The proxy recipe.** The nginx lines were not run against a real nginx, nor the Caddy line against Caddy. The same holds for everything in `docs/https.md`: its Caddy and nginx files and `tailscale serve` were not run, and basic auth in front of the page was ruled out by reading `src/client/api.ts`, not by trying it.
- **Versions of the saved state.** The runner is tested with fixture files and a made-up format that has three versions (every step, the copy, a failing step, a refused newer file, a folder of files, a copy that already exists, a home that cannot be written) and with each real file refused at version 2. No real file has had an upgrade yet: every format is still at version 1, so the first real step will be the first real use. Not tested: two gonogos on one home at the same moment (the lock keeps the second out before the runner), a disk that fills between the copy and the write.
- **Release.** Nothing was published: not the npm package, not the Docker image. `package.json` has no `repository`, `author`, `homepage` or `bugs`; the owner decides them before the first publish. `npm run check:pack` passed at the final check (it installs the packed tarball into a temporary folder from the npm registry).
- **Tests.** Three tests fail now and then and pass when run again: end-to-end scenarios 4 and 6 (pointer timing) on a heavily loaded machine, and the Uplink route test of a 256 KiB body (`write EPIPE`: the test client keeps writing after the server answered 413). All passed at the final check.
- **The browser, overall.** Every view was driven by script in Chrome (DOM events and the accessibility tree), never by hand on a real phone, never in Firefox or Safari, never with a screen reader.
