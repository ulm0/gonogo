## 1. Summary and recommendation

- **Build three small things, scoped to the project (the repo).** (A) verified claims, which gonogo flags stale; (B) one door: the room's rules plus the repo's own `AGENTS.md` reach every engine; (C) a closing checklist on a Mission, never a gate. No multivac integration of any kind.
- **One rule runs through all of it: gonogo reads the repo and never writes it, and treats everything it reads there as data, never as instructions** (RSO's M4). Where the claims live is the open storage question. (Engine Bay already says the same of the CLIs' own files: `docs/features/engine-bay.md:24`, "never in your project or the CLI's home".)
- **Port, do not import or run.** multivac has no library entry point and no types, and its evaluator, run the default way, rewrites the user's files. gonogo ports the anchor grammar, the regex gate and the matching it needs (MIT, the Director's own code, with a header naming the source) into its own modules, and fixes what multivac gets wrong for a server (no time limit on regexes). A table stays compatible with multivac's format, which costs nothing.
- **The one real danger is regexes from repo files.** I ran multivac's own verifier on a 40-character line against `/(a+)+$/`: it did not finish in 20 s (killed). gonogo must evaluate in a worker with a time limit, or one claim file freezes the server.
- **Order:** Door and Ritual first (small, no new store), Claims last (the big one, cuttable). Three PRs, about 1,200 lines in all. Open questions for the Director are in section 9.

## 2. What multivac is (read, and run)

**Purpose.** "Brain-driven development": one *brain* repo of claims, law and ritual, from which several code repos are developed; "deterministic verification, no model in the path" (`package.json`, `DESIGN.md`). Node 24+, MIT, dependencies `citty`, `picomatch`, `yaml`; npm package `multivac`, bins `multivac` and `mvac`; v0.15.0, still 0.x (I did not read its changelog; treat every minor as possibly breaking). It can be its own brain (`brain==code`: `repos: { brain: . }`), which is the shape gonogo would use for one project.

**Four commands matter here.** `init` (scaffold), `verify` (check claims against code), `doors` (project the agent door into harness files and install git hooks), `change new|plan|apply|land|close` (a change file crossing repos). The commands list also has `seed`, `count`, `doctor`, `repos`, `roadmap`, `help`.

| Job | Data and format | What I saw when I ran it |
|---|---|---|
| **Claims** | A table in `.multivac/invariants.md`: `\| ID \| statement \| authority \| state \| date \| source \|` (six columns, counted from the end because statements quote `\|`; `parseClaimRows`), and under each row **anchor comments**: `<!-- @anchor <ID> <repo>:<glob> [!<glob>] /<regex>/[i] [present\|absent\|unique\|count=N\|each\|each!] -->`. A claim may have several legs (AND). Globs are picomatch over `git ls-files`; regexes are one POSIX-ERE-like dialect, and `\s`, `\b` are refused with a hint. | 3 claims, 3 anchored, exit 0. **Importable as a library: no.**
- `package.json` has `bin`, `files: ["dist","skills"]`, and **no `main`, no `exports`, no `types`**. The published tarball (816 kB unpacked) has **no `.d.ts` files at all** (I counted: 0).
- The modules do export names: `parseAnchors`, `collectBrainAnchors`, `parseClaimRows`, `readClaimRows` (`anchor/parse`), `evaluateAnchors`, `RepoHandle`, `EvaluateOptions` (`anchor/evaluate`), `RepoScanner`, `scanLeg`, `scanWholeRepo`, `matchesInFile` (`anchor/match`), `ritualChecklist`, `ritualSeed` (`lib/ritual`), `linkDoor`, `CANONICAL_DOOR` (`doors/link`), `applyManagedBlock`, `renderBlock`, `stripManagedBlock` (`doors/block`). Node would resolve `multivac/dist/anchor/evaluate.js` (no `exports` map to forbid it), but it is not a supported surface.
- They are coupled to multivac's model: `evaluateAnchors` needs a `brainDir`, resolved repo handles and a `write` flag (**`write: true` edits the brain files**); `parseAnchors` reads `CHANGES_DIR` and `LAW_PATH` from `lib/config`; `collectBrainAnchors` walks the brain's `.multivac/` layout.
- **CLI-only:** `init`, `doors`, `change`, `seed`, `repos`, `doctor`, `roadmap`, and the report text of `verify` (no `--json` in the commands reference; the summary line `N blocking broken · exit N` at a line start is documented as stable).

**What the config and helpers can do (RSO's question; read `lib/regex.ts` and `lib/git.ts` in full, `lib/config.ts` by searching its keys and reading its repo-entry parser; not the rest).** `.multivac/config.yml` declares `repos.<key>` with `path`, `url`, `channel`, `role`, `sdd`, `managed`. A `path` can be any directory (so a config can point verification at another directory), a `url` is cloned by `repos sync`, and `DESIGN.md` says `repos sync` also installs declared tools: **from what I read I cannot show that a config cannot make multivac run commands or read outside the repo**, and I did not read all of `config.ts`. This is one more reason gonogo does not run it. Its git helper (`lib/git.ts`) uses `execFile` with no shell and strips ambient `GIT_DIR`/`GIT_INDEX_FILE`-style variables, but I saw no `core.fsmonitor`/`core.hooksPath` override. Its regex gate (`lib/regex.ts`) rejects `\s \d \w \b`, backreferences and unknown flags with a hint, and compiles the rest to a JS `RegExp`, so **nested quantifiers such as `(a+)+` are accepted**: that is the ReDoS I measured.

**Surprises worth knowing before gonogo touches it.** (1) `init`, `doors` and `change` **write the user's repo and its git config and make commits**; gonogo must never run them. (2) Default `verify` writes; only `--check` is read-only. (3) The regex engine has no time limit (probe above). (4) In a multivac repo, every commit an agent makes runs `.multivac/hooks/pre-commit` (verify) because of `core.hooksPath`; gonogo's co-author dispatcher already chains the repository's real hooks first (`src/server/coauthor.ts:44`, `git rev-parse --git-path hooks`), so a blocking claim can **fail an agent's commit**: that is the repo's policy, but the room should say so when it happens (open question 5). (5) `.claude/settings.json` in the repo adds Claude Code hooks; whether they merge with the settings gonogo passes to its agents was **not verified**.

## 4. The pieces

A **project** below means the git repository (top level, by `git rev-parse --show-toplevel`) of a directory. The same picking rules apply to every piece, so they are stated once.

**How the project is picked in a generalist room.**
1. **An agent:** the repo of its start directory `AgentRecord.dir` (`src/shared/protocol.ts:491`). A worktree or Clean Room agent has its own checkout, so it sees *its branch's* claims, which is right (claims travel with the code).
2. **An agent with no worktree:** the same, in the shared checkout; two agents in one checkout share the answer.
3. **A Mission:** an optional `repo` (absolute path) that defaults to the lead's repo at creation. **It must be the git top level of the start directory of an agent hired in this room** (M3): checked when it is set (the API refuses anything else) **and again every time it is read** (the agent may have been removed or its directory moved; then the mission has no repo). It only chooses the ritual template and the Knowledge block's grouping; it never names a path gonogo reads that no hired agent works in.
4. **A Task:** has no repo; it inherits its mission's, else its assignee's.
5. **An agent that works across two repos** (`dir` is the parent folder, not a repo; or it `cd`s elsewhere): **not followed**, said in the docs. `dir` outside any repo shows no knowledge. If that is too weak, add `AgentRecord.projects?: string[]` (extra repo directories); open question 3.
6. **Two projects in one task:** one task, two agents, two repos: each agent's tile shows its own repo's state; the Knowledge block lists each repo once (deduplicated by realpath).

### A. Verified claims (lessons anchored to code)

- **User value.** The thing agents most often get wrong is acting on stale knowledge ("we don't use X", "the limit is 5"). A claim with an anchor says which files must contain or not contain what; when code changes and the claim stops being true, the room says so at the moment work starts. No model in the loop; plain matching.
- **Data model.** `<repo>/.gonogo/claims.md`, **multivac's own table and anchor grammar** (six columns, `<!-- @anchor ... -->` legs, repo key `brain`), so the file can move under `.multivac/invariants.md` unchanged and back. gonogo supports modes `present`, `absent`, `unique`, `count=N`, `each`, `each!`; states ok, **stale** (a leg fails), **vacuous** (the glob, after exclusions, matches no tracked file), **unanchored**, **malformed** (file:line and the defect, never skipped). Row states: `active`, `proposed` (shown, never flagged), `retired` (ignored). `authority` is free text (multivac's values are `published|specified|open`; the builder reads `lib/config` to confirm). Not supported in v1: `moved` self-heal, `pending` (changes), `drift`.
- **Where files live: UNDECIDED, pending the Director (FLIGHT, m2066).** Two options are on the table, and this section's text below was written for the first:
  - *Option R (draft 2):* in the repo, `<repo>/.gonogo/claims.md`, versioned with the code; agents write claims by editing the file; gonogo only reads it. Only in repos where the user wants it.
  - *Option H (FLIGHT's proposal):* gonogo-owned, at `<GONOGO_DATA>/knowledge/<repo-id>/` (`repo-id` = normalized remote plus root commit; survives a deleted room), with `gonogo knowledge export` and `import`; optionally, per project, committed in `<repo>/.gonogo/` for the user's own repos.
  - *What the choice changes (not decided here):* H removes the symlink and agent-written-file risks for the claims themselves (S2 below still applies to the matched files) but agents then need a way to propose a claim (an API or tool, with the Director approving) because they can no longer just edit a file; claims no longer travel with a branch or a clone; the identity of a repo (`repo-id`) becomes a design problem (a repo with no remote, forks, a rewritten root); R keeps one source of truth with the code but puts agent-writable claims in front of other agents. The sections below hold for both unless they say R.
- **When it runs (cost).** Triggers: agent start; an agent's Stop hook, **debounced to once per 60 s per repo** and only when `.gonogo/claims.md` exists; Review open; a RECHECK key; never on a timer. A repo with no claims file costs one `stat`. Work: `git ls-files` (tens of ms for thousands of files), read each *matched* file once up to 1 MiB, one regex pass per leg. Bounds (RSO's M1): the evaluation runs in a **worker thread with `resourceLimits`** (heap and stack caps), **5 s in total** (the worker is terminated, the claim becomes `unevaluated: too slow`), **64 MiB of file bytes in total** per run, at most 20,000 files, 1 MiB per file, 200 rows; **one evaluation per repo at a time** (a trigger that arrives meanwhile is merged into one rerun); RECHECK and the file-change trigger are **rate limited** (at most one run per repo every 30 s whatever asks, the debounce above also applies to Stop). multivac's own run was 0.17 s on a tiny repo; I did not measure a large one.
- **Staleness.** The result is a function of the working tree (that is what multivac reads too), so it can be stale between triggers; the page shows "checked 40 s ago on `feature/x` @ abc1234". A claim edited by an agent in the same turn is re-read at the next trigger.
- **Failure modes.** A weak anchor (a word that appears everywhere) stays ok forever: gonogo shows the anchored count and the vacuous legs, and says in the docs it cannot judge meaning. A claim file with a typo is `malformed`, shown, never silently skipped. A repo in the middle of a rebase or an unreadable file: the check ends with "could not check: <reason>", never stale. Huge or binary files are skipped with a count.
- **Role and surfaces.** The role text gets **one fixed line** that contains nothing taken from the repo: "This project may hold verified claims; where they are and how to add one is in `docs/features/knowledge.md` of gonogo (the agent is told the file name by gonogo's own text, not by the repo)" (wording to be fixed with the storage decision). The start notice for an agent says only `knowledge: 2 stale, 1 vacuous` (**counts, never claim text**, M4). The agent tile shows a badge; the **Knowledge** block (new, in the room view) lists claims per repo with state and a link to the file in Hangar.
- **Cost: L** (about 600 lines): parser (about 120), evaluator and worker (about 200), cache and triggers, Knowledge block, tile badge, tests.

### B. One door for every engine

- **User value.** The same rules ("how we branch, how we report, never touch X") reach Claude Code, Codex, Gemini, opencode and the rest, without the user maintaining five files, and the room-wide ones do not have to be copied into every repo.
- **Data model.** Two sources, joined at agent start: **room rules** `<home>/rules.md` (text, 0600; edited in a Flight Rules block, in the room's home, so it is not in any repo). **Writes go through the API only, with step-up** (RSO's M5; `PUT /api/rules`, added to the step-up list of `docs/login-spec.md`), **audited** (a Downlink `info` line with who and the length, never the text), size cap 8 KiB, refused from an API key below scope `full`, and no agent route reads or writes the file and **project rules**, the repo's own `AGENTS.md` (or `CLAUDE.md` when that is all there is), which gonogo reads but never edits.
- **How gonogo delivers it.** Not by writing files. The room rules are added to the role text through the channel each engine already has (`providers.ts:181-232`). For the project rules: **a fixed pointer with no repo-derived text**, "The project's rules are in the file `AGENTS.md` in your working directory: read it first" (M4: no path, name or content from the repo; the agent already runs in that directory), added only for engines that do not load that file themselves; for engines that do, nothing (no duplicate). Whether each engine auto-loads `AGENTS.md` or `CLAUDE.md` is **not verified here**: from general knowledge Claude Code reads `CLAUDE.md`, Codex and opencode read `AGENTS.md`, Gemini reads `GEMINI.md` unless configured; the builder checks each CLI's current docs and `gonogo doctor` prints a table "reads AGENTS.md: yes / no / unknown".
- **Where it breaks.** An engine that takes no role text (a custom command has none; one engine has "no checked way to pass a role", see the comment at `providers.ts:232`): no door, said in the table. A huge `AGENTS.md`: only the pointer is injected, so nothing is cut. Two rules disagreeing (room says "squash", repo says "rebase"): the repo's wins by order in the text ("the project's rules win over the room's"); said once in the docs.
- **What multivac's `doors` do that gonogo will not:** write symlinks and managed blocks into the repo, install git hooks, add skills. The user can run `ln -s AGENTS.md CLAUDE.md` themselves; a print-only `gonogo doors` that prints the commands is a later option (like `gonogo expose`), not in this work.
- **Cost: S** (about 150 lines): rules store and block, the delivery, the doctor table.

### C. The closing ritual on a Mission

- **User value.** Missions end with "done" and nothing says what a good ending is. A short checklist ("the reviewer read it", "the changelog line is written", "the phone alert was tested") shown when the mission is closed is exactly multivac's "printed, not verified" idea, and it needs no checking logic.
- **Data model.** `Mission.ritual?: { text: string; done: boolean; by?: string; at?: number }[]` in `missions.json` (optional field; the file stays `version: 1`, as `keys` did for `agents.json`). At most 20 items of 200 characters, one line, control and bidi characters stripped. **The template is copied, not linked**, at creation: `<home>/ritual.md` (room default) first, then the project's ritual file (where it lives follows the storage decision; `.multivac/ritual.md` only if the Director says so, open question 2), read with the extraction of multivac's `ritualChecklist` (comments, headings and blank lines dropped). Editing the template later never changes an open mission.
- **Behavior.** **Only the Director's logged-in session ticks items** (RSO's M4): no agent tool, no `mission_update` field, no API key below scope `full` can set `done`. Items from a repo file are **labelled** on the page ("from the repo: ...") and cleaned as in S6, so a line an agent wrote cannot pass for the Director's own. **Never a gate:** the mission can become `done` with items open; the page says "2 of 5 closing items left" and the Downlink line for `done` lists them. The ritual is shown at the moment of closing, which is when it matters.
- **Project picking.** The repo of the mission's `repo`, else the lead's. If neither has a ritual file, the room default; if that is empty, no checklist at all.
- **Failure modes.** A template with 200 lines: first 20 taken, the rest dropped with a visible "20 of 200". An unreadable file: the room default.
- **Cost: S to M** (about 250 lines): field and validation, template read, page, Downlink line, tests.

### D. Detecting `.multivac/`: dropped

The Director's decision (m2066) is that gonogo owns the ideas and code and does not integrate with multivac: **no detection, no `multivac verify` row, nothing run from the `PATH`** (this also closes RSO's M6, and its question about what `.multivac/config.yml` can make multivac do). A repo that uses multivac is just a repo; its `.multivac/ritual.md` may still be read as a ritual template (a plain text file, cleaned as in S6), if the Director wants it (open question 2).

What is ported, and what is fixed on the way: the **anchor grammar and parser** (`parseAnchors`: legs, globs with `!` exclusions, modes) as is; the **regex gate** (`compileAnchorRegex`: POSIX-ERE-style, hints for `\s \d \w \b`, no backreferences, only the `i` flag) as is, **plus** a nested-quantifier refusal and the worker limits, which multivac lacks; **matching** (`matchesInFile`, the per-leg scan) re-written against read-only file reads and the safe git runner; the **ritual extraction** (six lines). Not ported: `evaluateAnchors`' rewriting of moved anchors, `init`, `doors` (they write the repo), `change`, `repos`, `seed`, the SDD adapters. A table in multivac's six-column format stays readable by multivac, but nothing in gonogo depends on it.

## 6. Security (RSO reads this section)

The new surface is **repo content an agent can write, read by gonogo and shown or acted on**. An agent in a repo, or anything that can make an agent write there (a prompt injection in a README, a dependency), controls: `.gonogo/claims.md`, `.gonogo/ritual.md`, `AGENTS.md`, `.multivac/*`, and the worktree's `.git/config` and symlinks.

| Threat | Why it is real | Must hold |
|---|---|---|
| **S1 Prompt-injection into other agents' door** (M4) | If gonogo pasted claims or `AGENTS.md` into the role text it would put agent-written text at **system-prompt authority** (`--append-system-prompt`, `providers.ts:226`) for every other agent on that repo. | **Repo text is data.** It never enters the role text, a pointer, a turn or a message: only fixed text, the room's own rules (the Director's file) and counts. The pointer to `AGENTS.md` is a fixed sentence with no repo-derived word. Agents read repo files as ordinary file reads, as they do today. A test checks that the role text, the start notice and every message built from a check contain no byte of `AGENTS.md`, `claims.md` or a ritual file. |
| **S2 Symlink and path escape** (M2) | A Clean Room agent (or any agent) can make `.gonogo/claims.md`, a ritual file or a matched file a symlink to `<home>/auth.json` or `~/.ssh/...`, or write a glob such as `../../..`; gonogo reads it and shows the result. | Every file is read through its **`realpath`, which must lie under the repo's realpath root, and opened with `O_NOFOLLOW`**, regular files only (as Hangar does, `hangar.ts:4`); files come from `git ls-files` and symlinks are skipped. A **glob** with `..`, an absolute path, `~` or a drive prefix is refused at parse. Test: a link to a file outside the repo is not read and not shown; each bad glob is `malformed`. |
| **S3 ReDoS and resource use** (M1) | Repo regexes run in gonogo. **Proven**: multivac's verifier did not finish `/(a+)+$/` on a 40-character line in 20 s. A hung evaluation freezes the Node event loop: every agent, hook and page of the room. | The bounds of section 4A: a worker with `resourceLimits`, **5 s in total** and 64 MiB of file bytes per run, **one evaluation per repo at a time**, rate limits on RECHECK and the mtime trigger; pattern at most 200 characters; line cap 4 KiB; no backreferences, no lookbehind, and **nested quantifiers refused at parse** (multivac's gate accepts them). A test runs `/(a+)+$/` and expects the worker ended, the claim `unevaluated`, and the server answering. |
| **S4 Git config executes programs** (M2) | A repo's `.git/config` (an agent can write it) can set `core.fsmonitor`, `core.hooksPath`, `diff.external`, `filter.*`; plain `git` commands in gonogo would run them. | Reuse the Recorder's runner (`recorder.ts:35`): **`-c core.fsmonitor=false -c core.hooksPath=/dev/null`**, `--literal-pathspecs`, no pager, **a clean environment with no `GIT_*` variable** (multivac's helper strips only some); only `ls-files`, `rev-parse`, `cat-file`; no `git grep` with textconv, no `diff`. |
| **S5 Room rules file** (M5) | `rules.md` is text that reaches every agent at system-prompt authority; whoever can write it controls all of them. | Only the API writes it, **with step-up, audited**, 8 KiB, scope `full` for keys; the file is 0600 in the room's home; no agent route reads or writes it. Test: a session without recent step-up gets 403; an agent token gets 404; the audit line has no text. |
| **S6 Display of untrusted text** (M4) | Claim statements, ritual items and file names appear in the page and could carry bidi marks, markup or a long social-engineering line ("run this command to fix"). | `textContent` only; strip control, bidi and zero-width characters (U+202A to U+202E, U+2066 to U+2069, U+200B to U+200F); cut to 200 characters; ritual items are plain text with no links and **labelled "from the repo"**; the start notice and the Downlink carry **counts, never text**; **only the Director's session ticks a ritual item**. |
| **S7 Writes into the repo** | Any write by gonogo into a repo changes the user's tree and could be steered by an agent. | **gonogo writes nothing in the repo** (this holds for Option R as well: only agents write claims). The only paths that change files are the ones that already exist (Hangar and Recorder at the Director's click). A test compares the tree before and after a check. |
| **S8 Resource use** | A repo with a million files or 10 GB. | The caps of section 4A; `git ls-files` through a stream with a byte cap; one evaluation per repo at a time; the debounce. |
| **S9 Stale trust** | A green "ok" next to a weak anchor is false comfort. | The page shows anchored count and vacuous legs; the docs say "ok means the pattern still matches, not that the sentence is true". |
| **S10 Hooks changing behavior** | In a repo with `.multivac/hooks`, an agent's commit can fail because of a blocking claim; multivac's `.claude/settings.json` hooks may feed failures to the agent. | Not gonogo's policy; but the room shows the failing hook's first line in the agent's tile when a commit is refused (existing hold/notice path), and the docs warn. |

Also required: the Knowledge block never renders a path outside the repo; **Mission.repo is validated as in section 4 (M3)** so a mission cannot make gonogo read a directory no hired agent works in. (S5 of draft 2, running the user's multivac, is gone with the decision of section 4D.)

## 7. What NOT to build

- **The brain repo as the entry point, the change gate ("no code outside a change"), spec-kit/OpenSpec adapters, forced landing order, `change apply/land` (worktrees per repo and merge requests).** They solve cross-repo coordination for a team that works *from* a brain; gonogo's rooms already have Missions, worktrees and Review, and the Director's constraint is N independent projects, not one ecosystem. A gate would also make `gonogo` refuse work, which it never does.
- **Any multivac dependency or integration:** import, running its CLI, or a multivac row (Director's decision).
- **Writing doors into repos** (`AGENTS.md` blocks, symlinks, `.claude/` hooks and skills, `core.hooksPath`). It changes the user's tree and git config; the pointer in the role text gets the same effect without a file.
- **Self-healing of moved anchors.** It writes files; in gonogo a `moved` leg is just reported (and only if cheap to detect; v1 says "stale").
- **A claim database in the room.** Claims are repo content; copying them into `<home>` makes two sources of truth.
- **Auto-written claims** (an agent that "learns" and files claims alone). A claim without a human-reviewed anchor is noise; the Director or an agent *in a reviewed commit* adds rows.
- **Per-engine door formats and skill installers.** Out of scope; the pointer works for all.
- **Blocking commits or tasks on stale claims.** Informational only.
- **A semantic or LLM judge of claims.** multivac's whole point is "no model in the path"; so is ours.
