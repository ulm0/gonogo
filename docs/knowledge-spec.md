## Intent and a push-back

Give gonogo's users three small things from multivac, **scoped to the project (the repo), never to the room**, because one room works on N projects. The room keeps how-we-work rules; a repo keeps what is true of its code; a Mission keeps its closing list. Only piece 1 is new to gonogo. Pieces 2 and 3 are small and worth doing even if piece 1 is cut. Do not build multivac's brain-repo, change gate or landing order: gonogo only detects a `.multivac/` and shows its state.

**One rule for all three: gonogo reads the repo and never writes it.** gonogo writes none of the user's project files today (only Hangar and Recorder at the Director's click). Agents already edit the repo; they write claims and rules like any file, and gonogo verifies them. No new write path.

## Piece 1: how it runs, and what must hold

- **Read-only evaluator, own code.** Files come from `git ls-files` through gonogo's safe git runner (no shell, hooks and fsmonitor off, no `GIT_*` of the process), matched with the claim's glob, **tracked files only, symlinks skipped, at most 20000 files and 1 MiB each**. Modes `present`, `absent`, `unique`, `count=N`, `each`, `each!` as multivac defines them. About 200 lines, no dependency (`node:fs` glob or the existing matcher: the builder checks which).
- **ReDoS.** The regex comes from a repo file, so a nasty pattern can freeze the event loop. The evaluator runs in a **worker thread**, killed after 5 s with the claim marked `unevaluated: too slow`; the pattern is at most 200 characters and compiled with the `u` flag only. A test runs `/(a+)+$/` against a long line and expects the worker killed and the server answering.
- **When.** On agent start, on Review open and on demand (a RECHECK key), cached by `HEAD` sha plus the mtime of `.gonogo/claims.md`. The result shows as `knowledge: 2 stale` on the agent's tile and a **Knowledge** block per project (the repos of the running agents, deduplicated by realpath). It is **said when work starts** (one line in the start notice of the agent) and never blocks: nothing gates a commit or a task.
- **Agents.** The role text gets one line: "This project's verified claims are in `.gonogo/claims.md`; read it; when you learn something that stays true of this code, add a row with an anchor." The pointer is the only content gonogo adds; it does not paste claims into the prompt.
- **A claim an agent writes badly** (anchor on a word that appears everywhere) stays `ok` forever: gonogo shows the anchored count and the `vacuous` legs and cannot judge meaning. Said in the docs.
- **Mission Log stays.** Mission Log is room-wide decisions (shared, not project-scoped); claims are facts tied to code. Nothing moves between them automatically.

## Can multivac's verify and doors be imported as a library? No (read, not run)

`package.json` (0.15.0, MIT, Node 24+, dependencies `citty`, `picomatch`, `yaml`) has **`bin` (`multivac`, `mvac` to `dist/cli.js`), `files` (`dist`, `skills`) and no `main`, no `exports`, no `types`**. So `import 'multivac'` has no entry point. The modules do have named exports (`parseAnchors`, `collectBrainAnchors`, `evaluateAnchors`, `RepoScanner`, `scanLeg`, `scanWholeRepo`, `ritualChecklist`, `linkDoor` with `CANONICAL_DOOR = 'AGENTS.md'`, `applyManagedBlock`, `renderBlock`), but they are internal: `evaluateAnchors` needs a `brainDir`, resolved repo handles and an `EvaluateOptions` (`write: true` **rewrites moved anchors in the brain files**), and `parseAnchors` pulls `CHANGES_DIR` and `LAW_PATH` from `lib/config`. A deep import of `multivac/dist/anchor/evaluate.js` would resolve (there is no exports map) but is unsupported, unstable across 0.x and drags a dependency and its config model into gonogo.
- **Pick: no import.** gonogo has its own small evaluator (piece 1) with the same grammar. When a repo has `.multivac/config.yml`, gonogo does **not** evaluate its claims itself: it runs `multivac verify --check --quiet` (never without `--check`, which would write) **if `multivac` is on the `PATH`**, no shell, 20 s limit, environment of `PATH` and `HOME` plus `GIT_CONFIG_COUNT` settings that turn hooks and fsmonitor off (env config wins over the repo's), reads the one summary line (`N blocking broken · exit N · ...`, which the reference says is stable at a line start; I found **no `--json` flag** in the reference) and shows it read-only as "multivac: 0 blocking broken, 12 claims". It never runs `init`, `doors`, `change` or `seed`. Only for repos the Director hired an agent into (the folder is already trusted by the hire).
- **Better for later:** if the Director adds an `exports` map for `anchor/*` and a `verify --json`, gonogo swaps the evaluator behind one function (`verifyClaims(repoDir)`). That is his call, in his repo.

## Reuse `.multivac/` or our own folder? Our own, and read the other

Writing into `.multivac/` would put gonogo's rows under multivac's governance (its table, its `projected.yml` "written by multivac, never by hand", its pre-commit hooks and change gate). A repo with `.multivac/` keeps it as it is: gonogo reads its `ritual.md` for the template and shows its verify state, and does **not** create `.gonogo/claims.md` there (the Director's claims live in multivac). A repo without it gets `.gonogo/` the first time an agent writes it. The shared grammar keeps the way open both ways: a table moves between the folders unchanged.

## Piece 2 detail: one door for every engine

Engines read different files (Claude Code `CLAUDE.md`; Codex and opencode `AGENTS.md`; Gemini `GEMINI.md`, configurable): **I did not verify the list; `gonogo doctor` prints a per-engine "reads AGENTS.md: yes / no / unknown", and the builder fills it from each CLI's current docs.** gonogo writes none of these files. For each agent at start: the **room rules** text (`<home>/rules.md`) is added to the role text, and, for an engine that does not load `AGENTS.md` itself, one line "The project's rules are in `AGENTS.md` at `<repo root>`: read it first" (a pointer, no duplicate for engines that auto-load). If the repo has no `AGENTS.md` and has `CLAUDE.md`, the pointer names that file. multivac's `doors` (symlinks and managed blocks in the repo) stay the user's choice: the docs say `ln -s AGENTS.md CLAUDE.md` is enough and a print-only `gonogo doors` is a later option, not part of this.

## Order of building

1. **Door (piece 2)**, S: rules file, Flight Rules block, pointer line, the doctor table. Value at once, no store, nothing to verify.
2. **Ritual (piece 3)**, S to M, in parallel with 1: independent files.
3. **Claims (piece 1)**, L, after both: the largest and the only one that reads repo contents with a repo-supplied regex; keeping it last lets the Director cut it without losing 1 and 2. Review by RSO before merge (worker, limits, path rules).
4. **`.multivac` state row**, S, with or after 3 (it shares the Knowledge block).
